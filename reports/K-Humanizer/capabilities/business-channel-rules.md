# 비즈니스 한국어 채널 규약

> 한국 고객 대상 글 5개 채널(B2B 영업 메일, 마케팅·광고, 랜딩·제품 페이지, 고객 지원·서비스 공지, 앱 UI·알림)마다 기본 어투와 주의점, 그리고 입력 모드별 합격 기준을 보여 주는 사례 17개를 정리한 지침이다.

## 1부. 동작 설명

### 1.1 한눈에 보는 흐름
1. 요청이 5개 채널 중 어디인지 정하고 해당 채널 절을 읽는다([response-format](./response-format.md) R-06).
2. 그 채널의 기본값(어투, 호칭, 문구 형태)을 적용한다. 기존 한국어 문구가 있으면 그것이 이긴다([situation-defaults-and-questions](./situation-defaults-and-questions.md) R-03).
3. 입력 모드에 맞는 사례와 비교해 고칠 곳과 그대로 둘 곳을 정한다.
4. 사실·조건은 [fact-protection](./fact-protection.md)대로 보호한다.

### 1.2 범위·통합 지점
- 제공: 채널별 기본값 문단 5개, 어휘 선택 원칙, 사례 17개의 합격 기준.
- 제외: 사례의 정확한 문구(동일 사실·조건·어투·독자 행동이면 다른 문구도 통과), 모드 판별([input-mode-and-authority](./input-mode-and-authority.md)), 일반 글쓰기 장르(feature map 행 8, 이번 범위 밖).
- 외부 의존·선행 계약: S1, S2, 어투 기본값 규칙.
- 소유 상태·부작용: 없음.

### 1.3 인터페이스와 데이터 의미
| 채널 | 기본 어투·형태 | 항상 지킬 것 |
|---|---|---|
| B2B 영업 메일 | 합쇼체. 수신자를 전체 이름+직함 또는 회사+직함으로 호칭. 쓰는 이유와 요청을 위쪽에 | 원문에 있는 각 요청을 분명하게. 긴박감·고객 사례·성과를 만들지 않는다 |
| 마케팅·광고 | 브랜드 어투를 따름. 헤드라인·배너는 명사구 가능 | 혜택은 그 조건·마감 옆에 둔다. 긴박감·희소성·최상급·사회적 증거를 추가하지 않는다 |
| 랜딩·제품 페이지 | 히어로는 독자가 할 수 있는 것을 말함. 사양표·기능 라벨은 짧은 명사구 | `최대`·`약` 같은 한정어, 가격·통화·VAT 문구는 원문 그대로 |
| 고객 지원·서비스 공지 | 공식 공지는 평이한 합쇼체, 지원 답변은 브랜드 어투 | 사과는 원문의 수준, 약속은 원문 그대로, 정책 한계와 예외 유지 |
| 앱 UI·알림 | 앱의 기존 문자열 어투에 맞춤 | 버튼은 동작을 이름으로. 키·변수·마크업 그대로. 삭제·결제의 실제 결과 유지 |

### 1.4 행동 규칙과 남은 질문
| ID | 조건·입력 | 반드시 관찰될 결과·사후 상태 | 검증 수준 |
|---|---|---|---|
| R-01 | 사례의 수정본 | 하나의 합격 답일 뿐 정확히 맞춰야 할 목표가 아니다. 같은 사실·조건·어투·독자 행동을 유지하면 다른 문구도 통과한다. 일부 사례의 정답은 입력을 그대로 돌려주는 것이다 | 코드 확인 |
| R-02 | 사례 설명 중 "Why this is better"와 영어 원문 | 독자에게 보여 주는 설명이며 응답 형식이 아니다. 응답은 수정된 한국어이고, 사례가 "Note returned with the result"를 보여 줄 때만 노트가 붙는다 | 코드 확인 |
| R-03 | B2B 영업 메일 | 합쇼체. 수신자는 전체 이름과 직함 또는 회사와 직함으로 호칭한다(이름만 부르면 영업 대상에게 너무 친근하다). 맥락이 이름·직함을 주면 쓴다. 쓰는 이유와 요청을 위쪽에 두고 각 요청을 분명히 한다. 긴박감·고객 언급·결과를 만들지 않는다 | 코드 확인 |
| R-04 | 마케팅·광고 | 브랜드 어투를 따른다. 헤드라인·배너는 명사구일 수 있다. 각 혜택을 조건·마감 옆에 둔다. 긴박감·희소성·최상급·사회적 증거를 추가하지 않는다. 대명사(`당신의`)로 시작하는 번역투 헤드라인은 대명사 없이 쓴다 | 코드 확인 |
| R-05 | 랜딩·제품 페이지 | 히어로는 독자가 할 수 있는 것을 말한다. 사양표·기능 라벨은 짧은 명사구로 두고, 이미 정확한 사양표는 그대로 둔다. `최대`·`약` 등 한정어와 가격·통화·VAT 문구를 원문대로 유지한다. 영어 `less than`은 `미만`의 의미를 유지하는 표현을 쓰고 경계값을 포함하는 `안에`로 바꾸지 않는다 | 코드 확인 |
| R-06 | 고객 지원·서비스 공지 | 공식 공지는 평이한 합쇼체. 지원 답변은 브랜드 어투를 따른다. 사과는 원문이 쓰는 수준으로 하고 원문에 없는 사과를 넣지 않는다. 약속은 정확히 원문대로 유지하고 정책 한계와 예외를 유지한다. 배송 단계의 용어(`출고`는 창고를 떠났다는 뜻)를 약속 범위에 맞게 고른다 | 코드 확인 |
| R-07 | 앱 UI·알림 | 앱의 기존 문자열 어투에 맞춘다. 버튼은 그것이 하는 동작을 이름으로 말한다. 키·변수·마크업은 그대로 둔다. 삭제나 결제 같은 동작의 실제 결과를 유지한다. 라벨은 설명으로 늘리지 않는다 | 코드 확인 |
| R-08 | 영어 직역이 현장 용어와 다르다 | 해당 분야 한국어 독자가 쓰는 용어로 바꾼다(`구현 지원`→`도입 지원`, `은행 조정`→`은행 거래 대사`, `당신의 장부`→`결산 마감`). 고객 어휘(`노쇼`, `라이더`, `리뷰`)는 유지하고, 제품이 쓰는 한국어 용어가 있으면 그것을 쓴다 | 코드 확인 |
| R-09 | 이미 자연스럽고 조건이 맞는 문구 | 바꾸지 않는다(갱신 안내, 사양표, 점검 공지, 현지 가격, 유효한 알림 문자열) | 코드 확인 |

- 불변식: 모든 채널에서 [fact-protection](./fact-protection.md)의 보호 항목이 어떤 어투 선택보다 우선한다.
- 미결정: 없음.
- 확인 한계: 지침 문장 확인이다. 사례 17개는 합성 사례이고 수정본은 모델 출력이 아니라 기대 행동의 예시라고 레포가 적는다(`business-korean.md:12-15`). 실제 모델이 이 사례들을 통과하는지는 레포의 2026-11-07 개발 점검(모델 채점, held-out 아님, [eval-procedure-and-records](./eval-procedure-and-records.md) R-10)에 있다. 점검에 쓴 fixture 케이스는 이 17개 사례와 다른 합성 케이스다.
