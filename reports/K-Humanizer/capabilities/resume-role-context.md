# 직무별 맥락

> 이력서 입력에 목표 직무·공고·분명한 직업적 맥락이 있을 때, 운영·기획·QA·디자인·마케팅·고객 응대·리서치·교육 8개 직무가 실제로 쓰는 말과 일을 지키면서 AI식 표현을 제거하게 하는 지침이다.

## 1부. 동작 설명

### 1.1 한눈에 보는 흐름
1. 이력서 규칙([resume-evidence-rewrite](./resume-evidence-rewrite.md))을 읽은 뒤, 입력에 목표 직무·공고·분명한 직업 맥락이 있으면 이 참조를 읽는다(`SKILL.md`의 "Read first"가 조건을 정한다).
2. 직무 표에서 보존할 경력 세부, 도움이 되는 증거, 피할 표현을 확인한다.
3. 인간화만 요청이면 경험 선택과 순서를 유지한다. 맞춤을 요청했으면 공고의 책임을 중심으로 검증된 증거를 정리한다.
4. 사실·기여 경계·측정 조건·완료 상태는 바꾸지 않는다.

### 1.2 범위·통합 지점
- 제공: 직무 표 8행, 직무별 "강한 bullet이 답하는 질문"(운영·기획·QA·디자인은 예시 포함), 공통 안전 규칙, 최종 직무 점검, 직무별 채점 점검.
- 제외: 재작성 일반 규칙([resume-evidence-rewrite](./resume-evidence-rewrite.md)), 작업 유형·맞춤 절차([resume-workflow](./resume-workflow.md)).
- 외부 의존·선행 계약: 이력서 증거 경계 스펙. 목표 직무가 없으면 이 참조는 쓰지 않는다.
- 소유 상태·부작용: 없음.

### 1.3 인터페이스와 데이터 의미
| 직무(`resume_role` 값 아님, 문서의 이름) | 보존할 세부 | 도움이 되는 증거 | 피할 것 |
|---|---|---|---|
| Operations | 반복 업무·예외·마감·인수인계·운영 판단 | 물량·빈도·기간·오류 유형·처리 시간·에스컬레이션 규칙·전후 관찰 | 바뀐 루틴이나 결과 없는 `운영 전반`, `원활한 운영`, `효율성 향상` |
| Service or product planning | 사용자·사업 문제, 고려한 선택지, 우선순위, 범위 결정, 검증 | 문의·행동 패턴, 요구사항, 트레이드오프, 정책, 출시 상태, 실험·피드백 결과 | 실제 결정 없는 `기획에 참여`, `니즈를 반영`, `방향성을 수립` |
| QA | 테스트 범위·환경·재현 조건·심각도·출시 결정·후속 조치 | 기기·시나리오 범위, 실패 조건, 결함 우선순위, 막힌 출시, 수정 검증, 재발 확인 | 테스트 케이스 수만, `품질을 강화`, 결함을 찾지 못한 점검을 결함으로 |
| Design | 사용자 과업, 정보 위계, 제약, 설계 결정, 검증 | 리서치 발견, 프로토타입, 사용성 과업, 디자인 시스템 규칙, 핸드오프 범위, 관찰된 과업 결과 | 설계 결정이나 증거 없는 `감각적인`, `트렌디한`, `사용자 경험 개선` |
| Marketing or content | 독자·채널·가설·메시지·배포·측정된 반응 | 도달 조건, 표본, 열람·클릭률, 전환 경계, 편집 결정, 귀속 출처 | 측정된 반응·출처 없는 `바이럴`, `브랜드 강화`, `성과 창출` |
| Customer service or sales | 고객 문제·정책·응대·후속·확인된 결과 | 문의 유형·건수·응답 시간·에스컬레이션·유지·만족의 측정 조건 | `친절한 응대`, `고객 만족 향상`, 회사 매출을 개인 영향처럼 |
| Research or data | 질문·방법·표본·한계·발견·뒷받침한 결정 | 데이터 출처·기간·표본·비교·분석 방법·불확실성 | `인사이트 도출`, `객관적 분석`, 상관을 인과처럼 |
| People operations or education | 학습자·팀 필요, 프로그램 결정, 진행, 참여, 후속 | 대상 규모·회차 수·수료·사내 설문·자료 소유·이후 채택 상태 | `역량 강화`, `성장 지원`, 파일럿에서 전사 도입을 추론 |

### 1.4 행동 규칙과 남은 질문
| ID | 조건·입력 | 반드시 관찰될 결과·사후 상태 | 검증 수준 |
|---|---|---|---|
| R-01 | 입력에 목표 직무·공고·분명한 직업 맥락 | 이력서 규칙 다음에 이 참조를 읽는다. 첫 임무는 분야의 실제 언어와 일을 지키면서 AI식 표현을 제거하는 것이다. 검증된 경험의 순서는 사용자가 맞춤을 요청할 때만 바꾸고 사실·기여 경계·측정 조건·완료 상태는 바꾸지 않는다 | 코드 확인 |
| R-02 | 직무 맥락 사용 | 직무 맥락은 확립된 용어와 일의 의미를 이해하는 데 쓴다. 인간화만 요청이면 경험 선택과 순서를 유지한다. 직무 지향 요청에서 공고가 여러 직무를 섞으면 공고의 책임을 중심으로 증거를 정리한다. 목표 직무가 없으면 추론하지 않고 일반 규칙을 쓴다. 공고의 책임을 경험으로 복사하지 않고 공고가 요구하는데 원본이 지지하지 않는 일은 공백으로 보이게 둔다 | 코드 확인 |
| R-03 | 직무별 bullet | 직무 표의 "보존할 세부"가 답을 가진 bullet을 강하다고 본다. 직무마다 같은 종류의 증거를 요구하지 않는다(질적 증거도 방법·결정이 분명하면 강한 증거) | 코드 확인 |
| R-04 | 직무 키워드·수치 | 직무 키워드는 맥락일 뿐 경험의 증명이 아니다. 숫자는 의미가 있어야 한다(`테스트 127건`, `콘텐츠 40건`, `문의 800건`은 범위·판단·결과와 연결되기 전까지 활동일 뿐). 제안·승인·파일럿·출시·조직 전체 도입을 구분하고, 팀 결과와 개인 소유를 구분한다. 질적 작업에서 분명한 결정과 방법은 지표 없이도 강한 증거이며 성숙해 보이려고 지표를 지어내지 않는다. 외부 독자가 필요한 분야 용어는 유지하고 낯선 내부 표현은 실제 과업·결정으로 풀어 쓴다 | 코드 확인 |
| R-05 | 직무 점검 | 표현이 분야의 실제 일을 일반적 성과 언어로 바꾸지 않았는가, 맞춤을 요청했다면 처음 두 bullet이 목표 직무의 주된 채용 질문에 답하는가, 섹션마다 다른 정보를 주는가, 판단과 책임을 보여 주는가, 약하거나 없는 경험이 공고 키워드로 덮이지 않았는가, 해당 분야 채용 담당이 사람이 실제로 무엇을 어떤 조건에서 했고 무엇이 확인됐는지 설명할 수 있는가 | 코드 확인 |
| R-06 | `resume_role`이 주어진 채점 | 직무별 채용 질문에 답하는지 본다: 운영(반복 업무·예외·인수인계·마감·운영 결과), 기획(문제·요구사항·우선순위·범위 결정·검증 상태), QA(범위·환경·재현 조건·심각도·출시 결정·후속), 디자인(사용자 과업·제약·설계 결정·핸드오프·사용성 증거), 마케팅(독자·채널·가설·메시지·귀속·측정 반응), 고객 응대(문제·정책·응대·에스컬레이션·후속·확인 결과), 리서치(질문·방법·표본·한계·발견·결정), 교육(학습자·팀 필요·프로그램 결정·진행·참여·이후 채택). 질적 증거가 강하면 퍼센트가 없다고 감점하지 않고, 행동·조건·결정 없이 직무 키워드만 들여오면 감점한다 | 코드 확인 |

- 불변식: 직무 키워드가 있어도 원본이 뒷받침하지 않는 경험·소유·결과는 추가되지 않는다(R-02, R-04).
- 미결정: 없음.
- 확인 한계: 지침 문장 확인이다. 직무별 골든셋 40건(직무마다 5건)과 그 점수는 이전 revision의 모델 채점이다. `resume_role` 필드 값은 스크립트가 쓰는 식별자(`marketing_content`, `customer_service`, `research_data`, `people_education` 등)이고 이 표의 직무 이름과 표기가 다르다([eval-fixtures-and-validators](./eval-fixtures-and-validators.md)).
