# 지원 동기

> 지원 동기·"왜 이 회사인가" 글에서, 검증된 경험 하나를 조직·직무의 구체적 일과 잇고 믿을 수 있는 기여를 설명하게 하며, 어느 조직에나 통하는 칭찬 글을 막는 지침이다.

<!-- 이 레포의 "구현"은 지침 문장이다. C-ID는 줄 범위, R-ID는 에이전트의 행동. 검증 수준 `코드 확인` = 지침 문장을 직접 읽음, LLM 실제 준수는 미확인. -->

## 1부. 동작 설명

### 1.1 한눈에 보는 흐름
1. 요청이 지원 동기·"왜 이 회사인가" 글이면 `application.md`를 읽는다(`SKILL.md`의 "Read first"가 조건을 정한다).
2. 쓰기 전에 하나의 연결을 정한다: 검증된 경험 → 그것이 드러낸 문제·일하는 방식 → 조직의 구체적 일 → 직무의 책임 → 지원자가 믿을 수 있게 기여할 수 있는 것.
3. 원본이 뒷받침하는 고리만 쓴다(다섯 부분이 모두 나올 필요는 없다).
4. 조직 이름을 다른 곳으로 바꿔 보고 그래도 문단이 성립하면 연결을 더 구체적으로 만든다. 비공개 회사 정보는 지어내지 않는다.

### 1.2 범위·통합 지점
- 제공: 지원 동기 규칙 7개와 진단 검사, 지원 글 작업의 완결 문장 원칙.
- 제외: 이력서 bullet 재작성([resume-evidence-rewrite](./resume-evidence-rewrite.md)), 섹션 역할·맞춤 절차([resume-workflow](./resume-workflow.md)).
- 외부 의존·선행 계약: 이력서 증거 경계 스펙(검증된 경험만 쓴다는 원칙).
- 소유 상태·부작용: 없음.

### 1.3 인터페이스와 데이터 의미
| 연산·데이터 | 입력·출력 / 타입 | 의미·제약 |
|---|---|---|
| 연결 5요소 | 경험 / 드러난 문제·방식 / 조직의 구체적 일 / 직무 책임 / 기여 | 원본이 지지하는 것만 사용. 모두 필요하지 않다 |
| 진단 검사 | 조직 이름 치환 → 문단이 여전히 성립하면 너무 일반적 | 해결: 제공된 공식 정보로 연결을 구체화하거나, 구체적 근거가 없으면 주장을 좁게 유지 |

### 1.4 행동 규칙과 남은 질문
| ID | 조건·입력 | 반드시 관찰될 결과·사후 상태 | 검증 수준 |
|---|---|---|---|
| R-01 | 지원 동기 글 | 목표는 실제 경험을 구체적 조직·직무와 연결하고 지원자가 믿을 수 있게 기여할 수 있는 것을 설명하는 것이다. 완결된 문장과 지원자의 실제 동기를 쓴다 | 코드 확인 |
| R-02 | 글의 시작 | 연대기적 자기소개가 아니라 방어 가능한 연결 하나로 시작한다 | 코드 확인 |
| R-03 | 연결 만들기 | 지원자의 실제 문제·선택·행동·배움을 조직의 구체적 일과 직무의 책임에 잇는다 | 코드 확인 |
| R-04 | 회사 칭찬 | 관련 없는 경험 옆에 두고 적합하다고 부르지 않는다. 회사에 대한 감탄이나 공고 문구를 개인 증거로 바꾸지 않는다 | 코드 확인 |
| R-05 | 관심 표명 | 제공된, 관심이 시작된 사건과 지원자가 이미 취한 행동으로 바꾼다. 관심 선언만 두지 않는다 | 코드 확인 |
| R-06 | 입사 후 기여 | 검증된 경험을 적용하는 것으로 설명하고 아직 확인할 수 없는 결과를 크게 약속하지 않는다 | 코드 확인 |
| R-07 | 진단 | 조직 이름을 다른 조직으로 바꿔도 문단이 그대로 성립하면 너무 일반적이다. 비공개 회사 정보를 지어내지 않고 제공된 공식 정보로 구체화하거나 근거가 없으면 주장을 좁게 유지한다 | 코드 확인 |
| R-08 | 평가 | 검증된 경험이 구체적 조직·직무 선택과 믿을 만한 기여를 설명하는지 본다. 일반적 회사 칭찬이면 감점. 원본이 조직 특유의 근거를 주지 않아 안전한 응답이 일반적이 되는 경우는 상한(Red Flag)을 적용하지 않고, 원본이 실제로 준 연결을 재사용 가능한 칭찬으로 바꿨을 때 상한을 적용한다 | 코드 확인 |

- 불변식: 글의 모든 연결은 원본이 지지하는 경험·행동에서 나온다(R-03, R-05, R-06).
- 미결정: 없음.
- 확인 한계: 지침 문장 확인이다. v0 골든셋의 `application_001`은 원본이 조직 특유의 근거를 주지 않아 일반적으로 남았고 낮은 실용성 점수가 기록돼 있다(`model-baseline.md`). 이 지침이 근거 없이 구체화하라고 요구하지 않는다는 해석은 R-08의 설명이 말한다.
