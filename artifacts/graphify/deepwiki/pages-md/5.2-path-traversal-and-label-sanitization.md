This section details the security mechanisms implemented to ensure that graphify remains a safe local development tool. The system employs strict path validation to prevent directory traversal, rigorous label sanitization to mitigate XSS and prompt injection, filesystem protections against symlink-based attacks, and execution guards for project file parsing and semantic fragment validation.

## Path Traversal Prevention

The primary defense against unauthorized file access is `validate_graph_path()`. This function ensures that any file operation initiated by the system (specifically via the MCP server or export modules) is restricted to the designated output directory.

### Implementation Details
The validation logic in `graphify/security.py` follows a "resolve and compare" strategy:
1.  **Base Enforcement**: It defaults the allowed base to the `graphify-out` directory relative to the current working directory [graphify/security.py:236-240]().
2.  **Existence Check**: It verifies that the base directory exists before proceeding, preventing callers from tricking the system into reading files before a graph has been built [graphify/security.py:241-245]().
3.  **Resolution**: Both the base and the target path are converted to absolute paths using `.resolve()` to neutralize `..` segments [graphify/security.py:248-250]().
4.  **Relative Verification**: It uses `Path.relative_to(base)` to check if the target resides within the base. If the path escapes the base, a `ValueError` is raised [graphify/security.py:252-258]().

### Usage in MCP Server
The `_load_graph` function in `serve.py` uses this guard to ensure that the JSON graph file requested by the Model Context Protocol (MCP) client is legitimate and resides within the allowed output directory [graphify/serve.py:143-154]().

### Symlink Protection
During the initial file discovery phase in `detect.py`, the system explicitly disables symlink following by not passing `followlinks=True` to directory walking utilities, ensuring the graph builder does not accidentally traverse into sensitive system directories or external volumes linked within the project root [graphify/detect.py:237-237]().

## Label Sanitization

Label sanitization is critical for two reasons: preventing Cross-Site Scripting (XSS) in interactive HTML visualizations and preventing prompt injection or formatting breakage when node data is returned to LLM agents.

### The `sanitize_label()` Function
All node labels and edge titles are passed through `sanitize_label()` before being exported or served [graphify/security.py:274-286]().

| Transformation | Implementation | Purpose |
| :--- | :--- | :--- |
| **Control Char Stripping** | `re.compile(r"[\x00-\x1f\x7f]")` | Removes null bytes and non-printable chars that break JSON or HTML [graphify/security.py:270-279](). |
| **Length Capping** | `_MAX_LABEL_LEN = 256` | Truncates labels to 256 characters to prevent buffer issues or visual clutter [graphify/security.py:271-281](). |
| **HTML Escaping** | `html.escape(text)` | Converts `<`, `>`, `&`, `"`, and `'` to entities to prevent XSS in `vis.js` output [graphify/security.py:282-282](). |

### Security Impact
*   **XSS Prevention**: Malicious code comments or function names (e.g., `<script>alert(1)</script>`) are rendered as plain text in the HTML visualization rather than being executed by the browser [graphify/security.py:282-282]().
*   **Prompt Integrity**: Sanitization ensures that node labels from user-controlled source files cannot break the text format returned to agents via the MCP server [graphify/security.py:279-281]().
*   **Metadata Cleaning**: The `sanitize_metadata` function recursively cleans dictionaries to ensure metadata associated with nodes (like descriptions or paths) adheres to length limits and contains no control characters [graphify/security.py:293-315]().

## XML & Project File Protection

When processing `.csproj` (C#) or Lazarus package files, graphify implements pre-screening to prevent XML-based Denial of Service (Billion Laughs attack).

### XML DoS Prevention
The extractors for `.csproj` and Lazarus packages check for malicious XML patterns before parsing:
*   **Pre-screening**: Functions like `extract_csproj` and `extract_lazarus_package` (in `extract.py`) scan the raw file text for `<!DOCTYPE` or `<!ENTITY` tags.
*   **Rejection**: If these tags are found, the extractor raises a `ValueError` to prevent the XML parser from expanding recursive entities [graphify/extract.py:1652-1657](), [graphify/extract.py:1754-1759]().

## Semantic Validation Limits

The `semantic_cleanup.py` module enforces strict limits on LLM-generated semantic fragments to prevent memory exhaustion and graph bloating.

| Constraint | Limit | Purpose |
| :--- | :--- | :--- |
| **Fragment Bytes** | `MAX_SEMANTIC_FRAGMENT_BYTES = 65536` | Limits the raw size of a single LLM-generated fragment [graphify/semantic_cleanup.py:21-21](). |
| **Fragment Nodes** | `MAX_SEMANTIC_FRAGMENT_NODES = 100` | Prevents a single file from generating an oversized semantic subgraph [graphify/semantic_cleanup.py:22-22](). |
| **ID Length** | `MAX_SEMANTIC_ID_LENGTH = 128` | Caps the length of semantic node IDs [graphify/semantic_cleanup.py:23-23](). |
| **ID Format** | `_SEMANTIC_ID_RE` | Enforces alphanumeric/underscore IDs to prevent injection in query strings [graphify/semantic_cleanup.py:24-24](). |

## Git Hook Execution Safety

When `graphify hook install` is executed, it configures shell scripts for `post-commit` and `post-checkout` events. These scripts include a robust Python interpreter detection block with built-in security constraints [graphify/hooks.py:34-72]().

### Shebang Allowlist in Discovery
During file detection, `graphify` uses an allowlist to identify valid code interpreters in extensionless files via their shebang line. This prevents the system from misclassifying or attempting to process arbitrary binaries as code [graphify/detect.py:87-92]().

The allowlist includes standard interpreters such as `python`, `node`, `ruby`, `perl`, `bash`, `lua`, and `php` [graphify/detect.py:88-91](). If a shebang is detected but the interpreter is not in the `_SHEBANG_CODE_INTERPRETERS` set, the file is not classified as `FileType.CODE` [graphify/detect.py:110-113]().

## Office File & Zip-Bomb Protection

To protect against malicious `.docx` or `.xlsx` files that may be designed to cause Out-of-Memory (OOM) crashes, `detect.py` implements a two-layer validation strategy in `_zip_within_caps()` [graphify/detect.py:57-92]().

1.  **Pre-filter**: Checks the declared sizes in the zip central directory against `_OFFICE_MAX_DECOMPRESSED_BYTES` (512 MiB) and `_OFFICE_MAX_COMPRESSION_RATIO` (200:1) [graphify/detect.py:76-79]().
2.  **Authoritative Pass**: Performs a bounded stream-decompression. If the actual uncompressed data exceeds the 512 MiB ceiling, the file is rejected [graphify/detect.py:81-89]().
