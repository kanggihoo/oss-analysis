This page provides a technical walkthrough of the `worked/example` corpus. This small-scale project serves as a reference for how `graphify` handles a multi-module Python application alongside architectural documentation. It demonstrates the transition from a linear document pipeline in code to a structured knowledge graph with identified hubs, "god nodes," and community clusters.

## Corpus Structure

The example corpus consists of 7 files representing a document ingestion system. The system follows a linear data flow: **Parser** $\rightarrow$ **Validator** $\rightarrow$ **Processor** $\rightarrow$ **Storage**, orchestrated by an **API** layer.

| File | Type | Responsibility | Key Symbols |
| :--- | :--- | :--- | :--- |
| `api.py` | Python | Entry point/Orchestration | `handle_upload`, `handle_search` |
| `parser.py` | Python | Format detection & ingestion | `parse_file`, `batch_parse` |
| `validator.py` | Python | Schema enforcement | `validate_document`, `ValidationError` |
| `processor.py` | Python | Enrichment & keyword extraction | `extract_keywords`, `enrich_document` |
| `storage.py` | Python | Persistence & indexing | `load_index`, `save_processed` |
| `architecture.md` | Markdown | Design decisions | N/A |
| `notes.md` | Markdown | Informal research/tradeoffs | N/A |

## Expected Graph Topology

When `graphify` processes this directory, it identifies structural roles for specific files based on their connectivity (degree) and position in the call graph.

### 1. Hubs and God Nodes
*   **`storage.py` (God Node):** Identified as the highest-degree god node because everything reads and writes through it. It persists data and maintains the index `[worked/example/README.md:42]()`.
*   **`api.py` (Hub Node):** Acts as the primary entry point, connecting to all four functional modules (`parser`, `validator`, `processor`, `storage`) to orchestrate requests `[worked/example/README.md:41-42]()`.

### 2. Community Structure
The Leiden algorithm typically detects two primary communities in this corpus:
1.  **The Logic Cluster:** The four Python modules (`parser.py`, `validator.py`, `processor.py`, `storage.py`) often cluster together due to their sequential call relationships `[worked/example/README.md:45]()`.
2.  **The Documentation Cluster:** `architecture.md` and `notes.md`. While they link to the code, their internal references to each other and lack of AST-level calls often place them in a secondary community `[worked/example/README.md:45]()`.
3.  **The API Cluster:** In some runs, `api.py` may be placed in its own cluster given its high connectivity to all other modules `[worked/example/README.md:45]()`.

## Technical Implementation Details

### Extraction Logic
*   **AST Extraction:** `graphify` uses tree-sitter to identify function calls and imports. It detects that `parser.py` calls `validator.py` and `storage.py` `[worked/example/README.md:43]()`.
*   **Markdown Extraction:** `graphify` parses the markdown files and identifies mentions of code modules, creating links between `architecture.md`/`notes.md` and the relevant Python files `[worked/example/README.md:44]()`.

### Graph Interaction (Sample Queries)
Once the graph is built in `graphify-out/`, the following technical queries can be resolved using the MCP server or CLI:

| Query | Resolution Logic |
| :--- | :--- |
| "what calls storage directly?" | Finds all incoming edges to the `storage.py` node or its functions `[worked/example/README.md:51]()`. |
| "what is the shortest path between parser and processor?" | Traverses dependencies, likely through `api.py` or the linear pipeline sequence `[worked/example/README.md:52]()`. |
| "which module has the most connections?" | Calculates node degree; `storage.py` typically wins `[worked/example/README.md:53]()`. |
| "what does the architecture doc say about the storage design?" | Traverses the edge from `architecture.md` to `storage.py` and retrieves the context `[worked/example/README.md:54]()`. |
