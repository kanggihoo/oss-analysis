This page describes event processing, enrichment, and masking logic within the Langfuse ingestion pipeline. After events are ingested via the API and retrieved from S3, they undergo transformation, validation, and enrichment before being written to ClickHouse. This process is primarily handled by the `IngestionService` and specialized processors for OpenTelemetry data.

## Processing Flow Overview

Event processing transforms raw ingestion events into enriched records. The `ingestionQueueProcessorBuilder` (for standard API events) and `otelIngestionQueueProcessor` (for OpenTelemetry events) retrieve payloads from S3 and process them through the enrichment layer.

## Ingestion Masking (Enterprise)

Langfuse supports masking sensitive data during the ingestion phase before it is persisted to ClickHouse. This is an enterprise feature implemented in the `@langfuse/ee` package and consumed by the worker.

1. **Header Propagation**: The API layer extracts specific headers defined in `LANGFUSE_INGESTION_MASKING_PROPAGATED_HEADERS` and propagates them to the worker via the queue payload.
2. **Execution**: If `isIngestionMaskingEnabled` returns true, the masking logic is applied to the event body via `applyIngestionMasking`.

## Event Record Enrichment

The `IngestionService.createEventRecord` function serves as the single point of transformation from loose `EventInput` to strict `EventRecordInsertType` [worker/src/services/IngestionService/index.ts:211-214](). It performs several critical enrichment steps:

*   **Prompt Lookup**: Resolves prompt references by name and version using the `PromptService` [worker/src/services/IngestionService/index.ts:226-233]().
*   **Model & Usage**: Resolves the model via `findModel` and calculates tokenization or cost if not provided by the SDK [worker/src/services/IngestionService/index.ts:235-236]().
*   **Metadata Flattening**: Transforms nested metadata into string records via `convertRecordValuesToString` [worker/src/services/IngestionService/utils.ts:45-54]().
*   **Timestamp Normalization**: Normalizes all incoming timestamps, such as converting JS Dates to ClickHouse-compatible formats [worker/src/services/IngestionService/index.ts:12-15]().

## Model Matching & Pricing

The system resolves model names provided in events to internal `Model` definitions to calculate costs.

### Model Resolution Flow
`findModel` is the primary entry point for resolving a model name to a database record and its associated pricing tiers. It utilizes a multi-layer cache (Local L1 + Redis L2) to optimize performance.

1. **Local Cache (L1)**: Checks `modelMatchLocalCache`.
2. **Redis Cache (L2)**: If L1 misses, it checks Redis using `getModelWithPricesFromRedis`.
3. **Postgres Lookup**: The system queries the `Model` table, matching the model name against regex patterns.
4. **Pricing Tiers**: Models are associated with `PricingTier` records which contain `Price` definitions for different usage types (input, output, total).

### Pricing Tiers & Cost Calculation
The `IngestionService` calculates usage costs by comparing user-provided costs against calculated costs based on resolved pricing [worker/src/services/IngestionService/tests/calculateTokenCost.unit.test.ts:143-152](). User-provided costs always take precedence over system-calculated ones [worker/src/services/IngestionService/tests/calculateTokenCost.unit.test.ts:180-183]().

## Event Attribute Extraction

During enrichment, specific domain-level attributes are extracted from the raw event body:

- **Tool Extraction**: `normalizeToolsForObservation` parses tool definitions and calls from the observation payload [worker/src/services/IngestionService/index.ts:50-51]().
- **JSON Deep Parsing**: `deepParseJson` and `deepParseJsonIterative` handle nested stringified JSON in inputs/outputs [packages/shared/src/utils/json.ts:61-79](). It includes `tryParsePythonDict` to handle Python-style dictionaries (e.g., from LangChain) by converting Python literals (`True`, `False`, `None`) to JSON [packages/shared/src/utils/json.ts:9-41]().
- **Usage Schema Transformation**: The system handles various usage formats (OpenAI completion vs. OpenAI response vs. standard Langfuse) and maps them to a unified internal `Usage` schema using Zod transforms [packages/shared/src/server/ingestion/types.ts:45-69]().
- **Score Inflation**: `validateAndInflateScore` resolves `configId` references to `ScoreConfig` to enforce data types (NUMERIC, CATEGORICAL, BOOLEAN, TEXT, CORRECTION) and maps categorical labels to numeric values [worker/src/services/IngestionService/index.ts:43-43]().

## Event Propagation (V4 Architecture)

The ingestion system increasingly uses an "events-first" architecture where observations are initially written to a staging table and later propagated to the primary events table.

*   **Staging Table**: `observations_batch_staging` acts as a temporary buffer with a 12-hour TTL [packages/shared/clickhouse/scripts/dev-tables.sh:81-130](). It uses 3-minute partitions to enable efficient batch processing [packages/shared/clickhouse/scripts/dev-tables.sh:121]().
*   **Propagation Job**: `handleEventPropagationJob` is a BullMQ worker that processes these partitions sequentially [worker/src/features/eventPropagation/handleEventPropagationJob.ts:58-60](). It joins staging observations with trace metadata to construct a full `events_full` record [worker/src/features/eventPropagation/handleEventPropagationJob.ts:140-185]().
*   **Cursor Management**: The job tracks progress in Redis using the `LAST_PROCESSED_PARTITION_KEY` to ensure no data is missed or double-processed [worker/src/features/eventPropagation/handleEventPropagationJob.ts:15-50]().
