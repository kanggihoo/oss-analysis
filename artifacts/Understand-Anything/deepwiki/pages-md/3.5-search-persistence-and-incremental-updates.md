This page details the mechanisms for searching within the Knowledge Graph, persisting the graph and related metadata to disk, and performing incremental updates to minimize re-analysis costs. It covers the `SearchEngine` (fuzzy search), `SemanticSearchEngine` (embedding-based search), the persistence layer (`readGraph`, `writeGraph`, `sanitiseFilePaths`), fingerprinting (`FileFingerprint`, `ChangeLevel`), the `change-classifier` (`SKIP`/`PARTIAL_UPDATE`/`ARCHITECTURE_UPDATE`/`FULL_UPDATE`), and staleness detection.

## Persistence Layer

The persistence layer is responsible for reading and writing the `KnowledgeGraph` and associated metadata to disk. All persistent data for a project is stored within a `.understand-anything/` directory at the project root. This directory is ignored by default in the ESLint configuration [eslint.config.mjs:13-13]().

### Directory Structure

All generated files are stored in the `.understand-anything/` directory within the project root.
```
.understand-anything/
├── knowledge-graph.json    // The main KnowledgeGraph
├── domain-graph.json       // The Domain Graph (if generated)
├── meta.json               // Metadata about the last analysis
├── fingerprints.json       // Structural fingerprints of analyzed files
└── config.json             // Project-specific configuration (e.g., auto-update preference)
```

### File Path Sanitization

A critical aspect of persistence is `sanitiseFilePaths` [understand-anything-plugin/packages/core/src/persistence/index.ts:38-67](). This function ensures that absolute file paths, which might contain sensitive user-specific information (e.g., `/Users/alice/company/src/auth.ts`), are converted to relative paths (e.g., `src/auth.ts`) before being written to `knowledge-graph.json`. If a path is absolute but outside the project root, only the filename is kept to minimize information leakage. This is applied to both the main `knowledge-graph.json` and `domain-graph.json` [understand-anything-plugin/packages/core/src/persistence/index.ts:76-76](), [understand-anything-plugin/packages/core/src/persistence/index.ts:154-154]().

## Incremental Updates and Staleness Detection

The system is designed to perform incremental updates to the Knowledge Graph, minimizing the need for full re-analysis and thus reducing token costs and processing time. This is achieved through a combination of fingerprinting, change classification, and automated hooks.

### Staleness Detection

Staleness detection is primarily handled by a `SessionStart` hook defined in `hooks.json` [understand-anything-plugin/hooks/hooks.json:14-25](). This hook checks if the `gitCommitHash` stored in `.understand-anything/meta.json` differs from the current `HEAD` commit. If they differ and `autoUpdate` is enabled in `config.json`, it triggers the auto-update workflow by instructing the LLM to read and execute `auto-update-prompt.md`.

- [understand-anything-plugin/hooks/hooks.json:14-25]()

### Auto-Update Workflow (`auto-update-prompt.md`)

The `auto-update-prompt.md` document outlines the detailed, multi-phase process for incrementally updating the Knowledge Graph. This prompt is triggered by Git commit hooks (`PostToolUse`) or session start if the graph is stale.

#### Phase 0 — Pre-flight (Zero Token Cost)

This phase performs initial checks and file filtering without involving any LLM tokens.
1.  **Graph Existence Check**: Verifies that `knowledge-graph.json` and `meta.json` exist.
2.  **Commit Hash Comparison**: Compares the stored `gitCommitHash` with the current `HEAD`. If they match, the graph is up-to-date.
3.  **Changed File Detection**: Uses `git diff` to identify files changed since the last analysis.
4.  **Source File Filtering**: Filters the changed files to include only relevant source code extensions (e.g., `.ts`, `.py`, `.go`).
5.  **`.understandignore` Exclusion**: Applies `.understandignore` rules to further filter out files that should not be analyzed, preventing unnecessary processing of ignored paths like test files or vendored code. This step uses a dynamically generated Node.js script (`ignore-filter.mjs`) to leverage the `createIgnoreFilter` utility from `@understand-anything/core` [understand-anything-plugin/hooks/auto-update-prompt.md:55-79]().

Sources:
- [understand-anything-plugin/hooks/auto-update-prompt.md:9-92]()

#### Phase 1 — Structural Fingerprint Check (Zero LLM Tokens)

This phase is crucial for determining the extent of changes using deterministic structural fingerprinting. It involves:
1.  **Fingerprint Loading**: Reads `fingerprints.json` [understand-anything-plugin/hooks/auto-update-prompt.md:101-101]().
2.  **Content Hashing**: For each changed file, computes a SHA-256 content hash. If the hash matches the stored one, the file is considered `NONE` (no change).
3.  **Structural Element Extraction**: Extracts structural elements (functions, classes, imports, exports) using regex patterns. This is a simplified, deterministic approach compared to the full Tree-Sitter analysis.
4.  **Change Level Classification**: Compares extracted elements against stored fingerprints to classify changes as `NONE`, `COSMETIC`, or `STRUCTURAL`.
5.  **New/Deleted File Handling**: New files are classified as `STRUCTURAL`. Deleted files (present in fingerprints but not on disk) are also `STRUCTURAL`.
6.  **Overall Update Decision**: Based on the aggregated file change levels, an `UpdateDecision` is made, which can be `SKIP`, `PARTIAL_UPDATE`, `ARCHITECTURE_UPDATE`, or `FULL_UPDATE`. The result is written to `change-analysis.json` [understand-anything-plugin/hooks/auto-update-prompt.md:121-121]().

### Fingerprinting (`FileFingerprint`, `FingerprintStore`)

The `fingerprint.ts` module defines the data structures and logic for creating and managing file fingerprints.

-   `FileFingerprint`: Represents the structural fingerprint of a single file [understand-anything-plugin/packages/core/src/fingerprint.ts:10-20](). It includes:
    -   `filePath`: Relative path to the file.
    -   `contentHash`: SHA-256 hash of the file's content.
    -   `functions`, `classes`, `imports`, `exports`: Arrays of names/identifiers for these structural elements.
    -   `totalLines`: Total lines in the file.
    -   `hasStructuralAnalysis`: Boolean indicating if the file was fully analyzed for structural elements.
-   `FingerprintStore`: A collection of `FileFingerprint` objects, along with metadata like `version`, `gitCommitHash`, and `generatedAt` [understand-anything-plugin/packages/core/src/fingerprint.ts:22-27]().

The `buildFingerprints` function [understand-anything-plugin/skills/understand/build-fingerprints.mjs:10-10]() (used by the auto-update prompt) is responsible for generating these fingerprints. It reads file content, computes hashes, and extracts structural elements using a combination of regex and potentially Tree-Sitter for more accurate analysis if available.

### Change Classification (`ChangeLevel`, `classifyUpdate`)

The `change-classifier.ts` module contains the `classifyUpdate` function, which takes a `ChangeAnalysis` (detailing new, deleted, and structurally changed files) and the total number of files in the graph to determine the appropriate update action.

-   `ChangeLevel`: An enum-like concept (though not explicitly an enum in `types.ts`) used internally to categorize file changes:
    -   `NONE`: No change.
    -   `COSMETIC`: Content changed, but structural elements (functions, classes, imports, exports) are identical.
    -   `STRUCTURAL`: Structural elements have changed.

-   `UpdateDecision`: The output of `classifyUpdate`, specifying the recommended action [understand-anything-plugin/packages/core/src/change-classifier.ts:4-10]():
    -   `action`: `SKIP`, `PARTIAL_UPDATE`, `ARCHITECTURE_UPDATE`, or `FULL_UPDATE`.
    -   `filesToReanalyze`: List of files requiring re-analysis.
    -   `rerunArchitecture`: Boolean indicating if architecture analysis needs to be re-run.
    -   `rerunTour`: Boolean indicating if the tour needs to be re-generated.
    -   `reason`: A human-readable explanation for the decision.

The `classifyUpdate` function [understand-anything-plugin/packages/core/src/change-classifier.ts:21-87]() implements a decision matrix:
-   **`SKIP`**: If no structural changes are detected (all files are `NONE` or `COSMETIC`).
-   **`PARTIAL_UPDATE`**: If some files have `STRUCTURAL` changes, but the directory structure is stable and the number of structural changes is small (≤10 files).
-   **`ARCHITECTURE_UPDATE`**: If new or deleted directories are detected (via `detectDirectoryChanges` [understand-anything-plugin/packages/core/src/change-classifier.ts:94-114]()), or if more than 10 structural files are changed. This triggers a re-run of the architecture analysis.
-   **`FULL_UPDATE`**: If a large number of structural changes occur (>30 files or >50% of the total graph files). This suggests a major refactor and recommends a complete rebuild.

## Search Engines

The system provides two primary search mechanisms: fuzzy search and semantic search.

### Fuzzy Search (`SearchEngine`)

The `SearchEngine` class (not explicitly provided in the snippets, but implied by usage in the dashboard) typically leverages a library like [Fuse.js](https://fusejs.io/) for fast, client-side fuzzy searching. It indexes `GraphNode` properties such as `name`, `summary`, and `tags`.

When a user types into a search bar, the `SearchEngine` quickly filters and ranks nodes based on their relevance to the query, even with typos or partial matches. This is commonly used for interactive filtering in the dashboard.

### Semantic Search (`SemanticSearchEngine`)

The `SemanticSearchEngine` (also implied by usage) performs search based on the semantic similarity of node descriptions or summaries. This requires pre-computed embeddings for each `GraphNode`. When a query is made, the query itself is embedded, and then a cosine similarity search is performed against the stored node embeddings. Nodes with high similarity scores are returned as results. This allows users to find related code entities even if they don't know the exact names or keywords, by describing what they are looking for in natural language.

This engine bridges the "Natural Language Space" (user query) to the "Code Entity Space" (GraphNodes) by using embeddings.

## Non-Code Parsers and Structural Analysis

While the core `TreeSitterPlugin` handles code languages, the system also includes specialized parsers for various non-code file types. These parsers contribute to the `StructuralAnalysis` by extracting `DefinitionInfo`, `ServiceInfo`, `EndpointInfo`, `StepInfo`, and `ResourceInfo` [understand-anything-plugin/packages/core/src/types.ts:129-160]().

Examples of such parsers include:
-   **`SQLParser`**: Extracts `table`, `view`, and `index` definitions from SQL files [understand-anything-plugin/packages/core/src/plugins/parsers/sql-parser.ts:26-73]().
-   **`GraphQLParser`**: Extracts `type`, `input`, `enum`, `interface`, `union`, `scalar` definitions and `Query`/`Mutation`/`Subscription` endpoints from GraphQL schema files [understand-anything-plugin/packages/core/src/plugins/parsers/graphql-parser.ts:25-53](), [understand-anything-plugin/packages/core/src/plugins/parsers/graphql-parser.ts:58-92]().
-   **`RubyExtractor`**: While primarily a code extractor, it demonstrates how language-specific structural elements (like `attr_accessor` for properties) are handled [understand-anything-plugin/packages/core/src/plugins/extractors/ruby-extractor.ts:15-15](), [understand-anything-plugin/packages/core/src/plugins/extractors/ruby-extractor.ts:100-164]().

These parsers implement the `AnalyzerPlugin` interface [understand-anything-plugin/packages/core/src/types.ts:195-203]() and populate the `StructuralAnalysis` object with their specific findings, which are then used to build the `KnowledgeGraph`.
