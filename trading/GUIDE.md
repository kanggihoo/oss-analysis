## 0. 목적과 범위

### 목적
업비트(코인)와 키움증권(국내·미국 주식)을 쓰는 개인 AI 트레이딩 시스템을 설계하기 위해, 오픈소스 AI 트레이딩 프로젝트들이 **무슨 데이터를 어떻게 모으고, AI가 그 데이터로 어떻게 판단하는지**를 코드 근거와 함께 정리한다.

### 우선순위 (높은 순)

| 순위 | 항목 | 핵심 질문 |
|---|---|---|
| 1 | 데이터 인벤토리 | 판단에 어떤 데이터를 쓰는가 |
| 2 | 수집 방식 | 그 데이터를 어디서, 어떻게 가져오는가 |
| 3 | 최신화와 스케줄링 | 데이터를 미리 쌓아 두고 주기적으로 갱신하는가, 판단할 때마다 가져오는가 |
| 4 | AI 판단 | 데이터를 LLM에 어떻게 넣고, 어떤 기준과 과정으로 최종 결정이 나오는가 |
| 5 | 실시간 리서치 | 판단 도중에 웹이나 뉴스를 따로 찾아보는가, 찾는다면 무엇을 어떻게 가져오는가 |

### 제외 범위 (조사하지 않음)

| 항목 | 제외하는 이유 |
|---|---|
| 알림 (Telegram, Slack 등) | 지금은 범위 밖 |
| 브로커 연동과 주문 실행의 내부 구현 | 우리는 키움 REST와 업비트 API를 쓰므로 필요 없음 |

예외로 다음 두 가지는 **짧게만** 기록한다.
- **판단 결과가 주문으로 넘어가는 경계**: 판단 결과의 형식, 비중을 정하는 코드, 사람 승인 단계가 있는지. 우리 주문 계층에 연결할 때 필요하기 때문이다.
- **UI**: 판단 근거를 화면에 어떻게 보여주는지만 기록한다.

### 2.2 고정 절차

```bash
cd ~/Desktop/oss-analysis/trading
git clone --filter=blob:none --no-checkout <url> repos/<name>
git -C repos/<name> fetch origin <sha>
git -C repos/<name> checkout <sha>          # detached HEAD
git -C repos/<name> rev-parse HEAD          # <sha>와 같은지 확인
git -C repos/<name> status --porcelain      # 비어 있어야 함 (clean)
```

지켜야 할 규칙:
- 분석하는 동안 `repos/<name>`에서 `pull`, 브랜치 이동, 파일 수정을 하지 않는다. **라인 번호는 고정 SHA에서만 유효하다.**
- SHA를 갱신하면 기존 보고서의 라인 번호가 틀어진다. 이때는 `reports/<repo>/`를 새로 쓰거나, 각 문서 머리의 SHA를 바꾸고 근거를 다시 검증한다.
- 클론한 코드는 **읽기만** 한다. 설치, 빌드, 실행을 하지 않는다. 실행 검증이 꼭 필요하면 사용자와 먼저 합의한다.

## 3. 근거 표기 규칙

### 3.1 위치 표기

모든 주장에는 근거 위치를 붙인다. 형식은 **`레포 루트 기준 상대경로:시작줄-끝줄`** 이다.

```text
tradingagents/agents/managers/portfolio_manager.py:42-78
```

- 함수나 클래스가 있으면 식별자도 함께 적는다: `` `create_portfolio_manager()` ``
- 핵심 근거 1~2개에는 SHA 고정 permalink를 붙인다.
  ```text
  https://github.com/<owner>/<repo>/blob/<sha>/<path>#L42-L78
  ```
- 라인 번호는 파일을 직접 열어 확인한 값만 적는다. grep 결과를 그대로 옮기지 않는다.
- 근거 표는 다음 형식으로 쓴다.

| 구분 | 위치 | 식별자 | 설명 | 검증 |
|---|---|---|---|---|
| 진입점 | `cli/main.py:120-160` | `analyze()` | 분석 시작 | 코드 확인 |

### 3.2 프롬프트 인용

판단 기준은 대부분 프롬프트 안에 있으므로 **원문을 인용**한다.

- 핵심 문장은 원문 그대로 짧게 인용하고, 바로 아래에 한국어 번역을 붙인다.
- 프롬프트가 길면 전문을 옮기지 않는다. 위치와 요약만 적고, 판단 규칙에 해당하는 문장만 인용한다.
- 프롬프트가 코드가 아니라 DB나 설정에 있으면(예: TradingAgents-CN의 `install/community_bootstrap.json`) 그 파일과 키 경로를 적는다.

### 3.3 검증 수준

상위 규칙과 같은 4단계를 쓴다.
- **`코드 확인`**: 코드를 직접 열어 확인함
- **`실행 확인`**: 실제로 실행해서 확인함
- **`추론`**: 코드 정황으로 짐작함. 반드시 근거를 함께 적는다.
- **`미확인`**: 확인하지 못함

README나 docs에만 있고 코드로 확인하지 못한 내용은 `추론`이나 `미확인`으로 표시한다. **README와 코드가 다르면 코드를 기준으로 삼고, 다르다는 사실을 기록한다.** 예를 들어 ai-hedge-fund는 루트 README는 v2를 설명하지만 `hedge_fund/README.md`는 이 SHA에 없는 v1 디렉터리(`src/`, `app/`)를 언급한다.

## 4. 공통 분석 항목

모든 레포에서 아래 항목을 같은 번호로 조사한다. 해당 사항이 없으면 "없음"과 그 근거(어디를 찾아봤는지)를 적는다. 없다는 것도 결과다.

### Q1. 데이터 인벤토리: 무엇을 보는가

판단에 들어가는 데이터를 **빠짐없이** 표로 만든다.

| 분류 | 데이터 / 필드 | 제공자 (API, 라이브러리) | 키 필요 | 소비 주체 (에이전트, 단계) | 근거 위치 |
|---|---|---|---|---|---|

분류 기준:
- 가격·거래량
- 기술지표 (지표명과 파라미터. 예: RSI 14, MA 5/10/20/60)
- 펀더멘털 (필드명)
- 수급·자금흐름
- 뉴스
- 감성·소셜
- 거시
- 코인 전용 (펀딩비, OI, 온체인, 공포탐욕지수)
- 포트폴리오·보유 현황
- 과거 판단과 메모리

함께 확인할 것:
- 정의만 있고 **실제로 아무도 쓰지 않는** 데이터 소스가 있는지. 호출하는 곳까지 grep해서 확인한다.
- 시장별로 쓰는 데이터가 다른지. 예: A주만 쓰는 수급 데이터.

### Q2. 수집 방식: 어떻게 가져오는가

- **수집 계층 구조**: 벤더 추상화, 라우터, 폴백 체인(1순위 실패 시 2순위). 우선순위는 어디서 설정하는가.
- **가져오는 방식**:
  - 미리 가져와 프롬프트에 넣는 방식(pre-fetch)인가
  - LLM이 도구를 호출해서 가져오는 방식(tool call)인가
  - 둘 다라면 데이터별로 어느 쪽인가
- **원시 데이터 가공**: 지표를 코드로 계산하는가 LLM에 맡기는가, 단위·부호·결측치 처리
- **캐시**: 위치, 키, 만료 기준
- **미래 데이터 차단(look-ahead 방지)**: 기준일 이후 데이터를 막는 장치. 백테스트 신뢰성과 직결된다.
- **호출 제한과 실패 처리**: 재시도, 백오프, 실패 시 판단을 계속하는지 멈추는지

### Q3. 최신화와 스케줄링

- **트리거**: 무엇이 분석을 시작시키는가. 수동 CLI / cron / GitHub Actions / APScheduler / Celery / 앱 내부 스케줄러 / 이벤트(가격 조건)
- **주기와 시점**: 예: 장 마감 후 18:00, 평일만, 거래일 캘린더 확인
- **사전 동기화**: 판단과 별도로 데이터를 DB에 미리 쌓는 작업이 있는가. 있다면 대상, 주기, 저장소(DB 종류와 테이블 또는 컬렉션)
- **데이터 신선도 관리**: 오래된(stale) 데이터를 감지하는가, 감지하면 판단에 어떻게 반영하는가(확신도 하향 등)
- **실시간 스트림**: WebSocket 등을 쓰는가, 판단에 쓰는가 화면 표시에만 쓰는가

### Q4. AI 판단: 어떻게 결정하는가 (가장 자세히)

**4-1. 입력 조립**
- 데이터를 프롬프트에 어떤 형식으로 넣는가: 텍스트 표, JSON, evidence manifest 등
- 길이 제한과 자르기 규칙
- 프롬프트를 만드는 함수의 위치

**4-2. 판단 흐름**
- 에이전트나 단계를 어떤 순서로 실행하는가. 병렬인지 순차인지
- 토론 라운드 수, 종료 조건
- 모델 계층: quick 모델과 deep 모델을 어디에 쓰는가
- 흐름을 정의한 코드의 위치. 그래프 정의, 오케스트레이터
- 흐름을 **mermaid 다이어그램 1개**로 그린다.

**4-3. 결정 기준**
- 프롬프트에 적힌 판단 규칙. 원문 인용과 번역(3.2절)
- **숫자로 된 임계값과 공식**. 예: MA5 대비 5% 초과 시 추격 금지, 점수 구간, 비중 공식
- 페르소나나 역할별 기준의 차이

**4-4. 출력 형식**
- 결정 스키마: 필드명, 타입, 값 범위
- 등급 체계. 예: Buy, Overweight, Hold, Underweight, Sell
- 확신도와 점수
- 진입가, 손절가, 목표가, 비중

**4-5. 최종 결정이 만들어지는 방식**
- 최종 결정을 **LLM이 정하는가, 결정적 코드가 정하는가**
- 코드가 LLM 결과를 덮어쓰거나 제한하는 장치: 가드레일, 한도, 규칙 기반 덮어쓰기
- 여러 신호를 합치는 방식: 가중평균, 다수결, 토론 결론

**4-6. 실패 처리**
- 파싱 실패, 데이터 누락, LLM 오류가 나면 어떻게 되는가: 기권 / Hold / 거래 불가 / 그대로 통과(fail-open)

**4-7. 메모리와 사후 채점**
- 과거 판단을 저장하는가
- 사후에 수익률로 채점하는가. 기간과 벤치마크
- 채점 결과(교훈)를 다음 판단의 어느 단계에 넣는가

**4-8. 비용**
- 판단 1회당 LLM 호출 수의 근사치. 계산 근거를 함께 적는다.

### Q5. 실시간 리서치

- 판단 도중에 웹 검색, 뉴스 검색, 웹 페이지 읽기, 공시 조회를 하는가
- **제공자**: Tavily, SerpAPI, Exa, DDG, RSS, SEC 등. 키가 필요한가
- **호출 방식**:
  - 고정된 검색어 목록으로 검색하는가, LLM이 검색어를 직접 만드는가
  - 몇 차원에서 몇 번 검색하는가
- **결과 처리**: 요약, 잘라내기, 출처나 시점 표기, 중복 제거
- **신뢰성 장치**: "숫자는 도구 결과에서만 가져온다" 같은 규칙, 인용 ID, 반복 검색 방지
- 리서치 루프의 종료 조건: 반복 상한, 시간 제한

### Q6. 경계 기록 (짧게)

- **판단 → 주문 경계**:
  - 판단 결과를 주문으로 바꾸는 코드가 있는가
  - 사람 승인 단계가 있는가. 기본값은 무엇인가
  - 하드 리스크 한도: 종목당 상한, 일일 한도, 킬스위치
- **판단 근거를 보여주는 UI**: 화면 이름과 표시 항목을 3줄 이내로 적는다.

### Q7. 우리 시스템에 적용 (분석자 의견)

- 가져갈 것 / 버릴 것
- 업비트·키움 데이터로 대체할 항목. 예: 수급 → 키움 `ka10059`, 재무 → DART
- 라이선스상 코드 재사용이 가능한가, 아이디어만 참고해야 하는가

이 항목은 코드 근거가 아니라 **분석자 의견**이므로 문서 안에 "의견"이라고 명시한다.

## 6. 산출물 형식: `reports/<repo>/`

```text
reports/<repo>/
├── 00-overview.md         # 입구: 메타데이터, 한눈 요약, 판단 흐름 다이어그램, 각 문서 링크
├── 01-data.md             # Q1 데이터 인벤토리 + Q2 수집 방식
├── 02-schedule.md         # Q3 최신화와 스케줄링
├── 03-decision.md         # Q4 AI 판단 (가장 긴 문서)
├── 04-research.md         # Q5 실시간 리서치
├── 05-boundary-and-fit.md # Q6 경계 + Q7 적용 의견
└── next.md                # 확인한 범위, 미확인 항목, 다음에 볼 파일
```

- 문서는 판단 흐름 순서대로 읽히게 번호를 붙인다.
- 레포별 중점(5절) 때문에 내용이 많아지면 `03-decision/` 같은 하위 폴더로 나눠도 된다.

### 6.1 모든 문서 머리

```markdown
# <repo> — <주제>

- 분석 SHA: `<sha>` (repos.lock.tsv와 일치해야 함)
- 분석일: YYYY-MM-DD
- 관련 공통 항목: Q4
- 검증 수준 요약: 코드 확인 N / 추론 N / 미확인 N
```

### 6.2 `00-overview.md` 필수 섹션

1. **메타데이터**: URL, SHA, 커밋일, 라이선스, 주 언어, 대상 시장, 지원 LLM
2. **한 줄 정의**: 이 레포가 무엇이고, 판단 주체가 LLM인지 코드인지
3. **판단 파이프라인 다이어그램**(mermaid): 데이터 수집 → 분석 → 결정 → 출력
4. **핵심 발견 5개**: 각각 근거 위치 포함
5. **공통 항목 요약표**: 항목별 2줄 요약과 상세 문서 링크

   | 항목 | 요약 | 문서 |
   |---|---|---|
   | Q1 데이터 | … | [01-data.md](01-data.md#q1) |

## 8. 진행 순서와 완료 기준

### 진행 순서
1. **레포 하나 시작**: 2.2절 절차로 SHA를 고정하고 `00-overview.md`의 메타데이터를 채운다.
2. **진입점부터 추적**: CLI, API, 스케줄러 중 판단이 시작되는 지점에서 출발해 최종 결정이 나오는 지점까지 따라간다(Q4-2).
3. **데이터를 역추적**: 판단에 들어간 입력을 거꾸로 따라가 Q1 → Q2 → Q3 순으로 채운다.
4. **Q5, Q6, Q7**을 채운다.
5. **`next.md`**를 정리한다.
6. 8개가 끝나면 **`comparisons/`**를 작성한다.

권장 레포 순서: **TradingAgents → ai-hedge-fund → daily_stock_analysis → QuantDinger → Vibe-Trading → dexter → OpenAlice → TradingAgents-CN**. 판단 구조가 뚜렷한 레포부터 보고, 원본과의 차이로 분석할 CN 버전은 마지막에 둔다.

### 레포 하나의 완료 기준
- [ ] 모든 문서 머리의 SHA가 `repos.lock.tsv`와 같다.
- [ ] Q1 표에 정의만 있고 쓰이지 않는 데이터가 구분돼 있다.
- [ ] Q4 판단 흐름 다이어그램이 있고, 노드마다 코드 위치가 있다.
- [ ] 판단 규칙과 임계값이 원문 인용, 번역, `파일:라인`과 함께 있다.
- [ ] "최종 결정은 LLM인가 코드인가"에 한 문장으로 답했다.
- [ ] 모든 주장에 검증 수준이 붙어 있고, `추론`에는 근거가 있다.
- [ ] README와 코드가 다른 곳이 기록돼 있다.
