# 메모리 verbs 7개와 프로토콜 (remember · recall · entity · synthesize · forget · context_pack · delta)

> 에이전트가 MCP 도구(또는 CLI)로 `remember`(사실 한 건을 출처와 함께 저장)·`recall`(사실과 페이지 조회)·`entity`(엔티티 카드)·`synthesize`(LLM 종합 답)·`forget`(사실 철회)·`context_pack`(세션 시작용 묶음)·`delta`(이후 바뀐 것)를 부르면, 서버가 검증·중복 판정·저장 또는 예산 안에서 모은 결과를 `protocol_version: 1` 봉투로 돌려주고, `--surface verbs`는 이 7개만 노출하며 `gbrain protocol conformance`가 서버가 이 계약을 지키는지 검사한다.

## 1부. 동작 설명

### 1.1 한눈에 보는 흐름

질문 ①의 사실(fact) 쪽 답은 흐름 A, 질문 ③의 뒤 절반("필요한 것만 가져와 LLM에게 건네는 모양")은 흐름 B·C, 질문 ②의 MCP 도구 쪽 답(에이전트가 언제 부르게 되는가)은 R-05~R-07이다. 앞 절반(검색)은 [hybrid-search](./hybrid-search.md)다.

**흐름 A. `remember(fact, provenance, entity?)`** (대표 쓰기, 가정: 엔티티 페이지가 이미 있고 파일 쓰기가 켜져 있음)

1. 입구 검증(R-10): `fact`·`provenance`(출처 필수)·`kind`·`visibility`·`valid_from`·`replaces` 형식을 검사한다. 어긋나면 저널에 아무것도 넣지 않고 `invalid_params`/`provenance_required`/`not_found`로 거절한다.
2. 접수 전 해석(R-12~R-14, R-17~R-20): 소스 활성 확인, `ttl`→`valid_until`, 엔티티 해석(명시 `entity` 또는 본문 속 정확한 언급으로 추론), 대상 페이지(`<entity slug>` 또는 `memory/unattributed`)와 파일 쓰기 여부 결정, 철회된 주장과 `replaces` 사전 검사. 통과하면 의도(intent)를 쓰기 저널에 접수한다([page-storage R-30·R-31](./page-storage-and-import.md)).
3. 소비자 준비(R-16, R-17): 사실 임베딩을 만들고(키 없으면 건너뜀, R-23), 같은 주장(정확 지문) 또는 같은 엔티티의 거의 같은 주장(코사인)이면 `duplicate`/`superseded`로 판정하고, `## Facts` 펜스에 행을 덧붙인 페이지 본문을 렌더·청킹한다.
4. 발행(page-storage R-04): 한 트랜잭션 안에서 (파일을 쓰는 경우) 파일 교체 → 페이지 본문 갱신 → `facts` 행 INSERT(펜스 행 번호 `row_num`, `source_markdown_slug` 포함) → 대체된 옛 행 만료 → 영수증 `committed`(R-16).
5. 응답(R-24): `{id, status(inserted|duplicate|superseded), status_text, entity_slug, valid_until, protocol_version, write_request}`. 시간 안에 못 끝나면 `unavailable`+`write_pending`(R-03).
6. 커밋 뒤 effect(청크 임베딩·git)는 page-storage R-07·R-22가 정한다. 이 스펙의 `facts` 행 임베딩은 2~3단계에서 이미 계산된다.

**흐름 B. `context_pack(entities, budget_tokens)`** (대표 읽기 묶음)

1. 입력 정리(R-38): `entities`(쉼표 목록, 최대 8)·`since`·`include_private`(로컬만)·`budget_tokens`(양수일 때만 예산 적용).
2. 이름마다 카드 조립(R-39): 엔티티 카드(요약 160자, 열린 스레드 ≤3, 간선 ≤10, 카드별 최신 사실 ≤5) → 소스 전체의 핫 메모리 사실(상위 10) → (기본 켜짐) 더 새로운 언급 페이지.
3. 앞에 코어 블록(기본 꺼짐)·pull brief(`counterparty` 줄 때만)를 붙인다(R-42).
4. 예산 포장(R-41): 머리글 비용을 먼저 떼고 카드 → 카드의 엔티티 사실 → 핫 사실 → 언급 → 레코드 순으로 담는다. 각 단계는 앞에서부터 잘라 넣고 처음 못 들어가는 항목에서 멈춘다.
5. 주입용 `text`(봉투 주석 + 섹션별 줄)를 최종 집합에서 다시 렌더하고 `budget_used = estimateTokens(text)`를 낸다(R-40).

**흐름 C. `recall(entity | since | session_id | question, query?, budget_tokens?)`**

1. 소스 범위·가시성(원격이면 world 사실만)·신뢰 하한을 정한다(R-31, R-48).
2. 사실 팔: `question`이면 관련도 순위, 아니면 `supersessions`/`since`/`entity`/`session_id`/무필터 중 하나로 사실을 읽는다(R-30~R-32).
3. 페이지 팔: `query`가 있으면 [hybrid-search R-90](./hybrid-search.md)대로 검색(확장 없음)하거나, 키·임베딩이 없으면 키워드만(R-33).
4. `budget_tokens`가 있으면 사실을 먼저(또는 `query_first`면 페이지 결과를 먼저) 예산에 담는다(R-34).
5. `{facts[], total, protocol_version, results?, budget_*?, budget_packing?}`로 반환한다(R-35).

**흐름 D. `delta(since | cursor | session_id)`**: 세 팔(바뀐 페이지, 새 사실, 스레드 사건)을 각자의 키셋 위치부터 읽고 예산에 맞춰 자르고, 실제로 전달한 만큼만 커서를 전진시켜 다음 호출이 이어받게 한다(R-44~R-47).

### 1.2 범위·통합 지점

- 제공: 7개 verb 각각의 입력·출력·실패 코드(대표 `remember`, `context_pack`), 사실이 `## Facts` 펜스와 `facts` 행에 쓰이는 규칙, 예산 포장 규칙, `--surface` 노출 범위, 서버 instructions·도구 설명 텍스트, `gbrain protocol conformance`의 검사 범위, 에이전트가 부르는 `remember`와 서버가 자동으로 저장하는 경로의 경계(R-49).
- 제외(이유):
  - **자동 사실 추출**(`extract_facts` 도구, `facts-backstop` effect, Stop-hook·context-engine·checkpoint·sweep 경로, `dream`의 사실 단계, `memory.auto_writeback`의 지시문 본문): 지도 12행. 여기서는 경계만 R-49에 한 줄씩 적는다. 주의: `extract_facts`는 기본 설치에서 전체 surface에 노출되고 `facts.extraction_enabled` 미설정이면 켜져 있다(R-49).
  - **훅 기반 push**(`context-pack-handler`, `volunteer_context`, `_meta.brain_hot_memory`의 소비 쪽 설정): 지도 16행. `_meta.brain_hot_memory`가 응답에 붙는다는 사실만 R-39에 적는다.
  - **신뢰 등급 쓰기 게이트·내용 위생·`contested` 처리·`content_origin`의 효과**: 지도 13행. `min_trust`·`trust.*`·가시성이 읽기 결과에 미치는 필터 규칙만 R-48에 둔다.
  - **`synthesize`의 내부**(`runThink` 수집·합성·인용 검증): 지도 7행(`think`). 이 verb의 입출력·오류 변환만 R-37.
  - **`entity` 카드의 참조 그룹(`referenced_by`·`records`·`coverage`)·`text_mentions`·정체 형제 표시 내부**, `resolvePhantomCanonical`·`tryPrefixExpansion`(phantom 페이지 병합 경로, 사실 추출 쪽 소관), 활성 스키마 팩 로딩(`loadActivePackForEngine`)과 `mentions.*` 정책 값의 출처: 입력으로 취급한다(해소가 쓰는 "링크 가능 엔티티 타입 집합"은 R-59에서 기본값과 결합 규칙을 정의하고, 팩 매니페스트를 읽는 코드는 범위 밖). 엔티티 이름 해소 자체(느슨·엄격 체인, 별칭, 접두 확장, 이름 변형, 카드 후보 선택, 형제 판정)는 R-50~R-59에서 정의한다.
  - **`context_pack`의 부가 단계**(아래 표). 기본 설치에서 켜진 단계가 있으므로 **이 스펙의 코어만으로는 기본 설치의 `context_pack` 출력과 같아지지 않는다**(코어 계약 = 카드·열린 스레드·핫 사실·예산 규칙만 재현 범위).
  - `gbrain recall`의 CLI 전용 모양(`--today`, `--watch`, `--rollup`, `--since-last-run`, `--as-context`, `--pending`)과 `gbrain forget --purge`: CLI 어댑터. 어느 형태가 verb 연산을 거치는지만 R-30에 둔다.
  - 저널 소비자 내부(claim·lease·복구), `persistence/` 나머지: [page-storage-and-import](./page-storage-and-import.md) 확인 한계와 같다.
- 부가 단계(`context_pack`, 코어 밖). 각 근거는 2.1.

  | 단계 | 기본 | 출력에 미치는 효과 |
  |---|---|---|
  | 더 새로운 언급(`newer_mentions`) | 켜짐(`mentions.newer_on_cards`가 `false/0/off/no`가 아니면, 팩 전체 6000자) | 카드 뒤에 "이 엔티티 페이지보다 새로운 날짜의 페이지" 블록을 `text`에 붙임. 예산에서는 카드·사실 다음 차례로 담김 |
  | 참조·레코드(`referenced_by_count`, `records`) | 레코드 타입을 등록해야(`entity.record_types`) 레코드가 나옴 | 예산 맨 마지막 차례. 못 들어가면 카드에 개수만 남김 |
  | 코어 메모리 블록 | **꺼짐**(`memory.core.enabled` 미설정=거짓, 켜면 기본 4000자) | `text` 맨 앞. 예산에서 먼저 차감하지만 코어 자체는 잘리지 않음(R-41) |
  | pull brief(`counterparty`) | `counterparty`를 줄 때만 | 코어 다음에 붙음. 예산에서 먼저 차감 |
  | 고정 질문(`pinned_questions`, `withheld`) | 소유자 권한 호출자만 | `text`·예산 밖 |
  | 카드의 `page_status`, 별칭 출처 알림 | `entity.row_page_status` 기본 켜짐 | 카드 필드만 늘어남 |

- 외부 의존·선행 계약:
  - [page-storage-and-import](./page-storage-and-import.md): 모든 쓰기는 `submitPageMutation` 계열 저널 한 입구(R-01), 영수증 상태와 `request_id`·`expected_revision` 의미(R-30~R-35), 파일 쓰기 결정(R-02~R-07)을 그대로 쓴다. `put_page`와 달리 `remember`·`forget`은 접수 시점이 다르다(R-26).
  - [hybrid-search](./hybrid-search.md): `recall`의 `query` 팔이 `hybridSearchCached`를 `expansion:false`로 부른다(R-90). 점수·청크 행·토큰 예산 규칙은 그쪽(R-30~R-37)이고, 이 스펙의 `packToBudget`은 "첫 초과에서 멈춤"인 다른 포장기다(R-34).
  - [engine-and-schema](./engine-and-schema.md) 1.3: `facts` 테이블 컬럼(`row_num`, `source_markdown_slug`, `expired_at`, `superseded_by`, `trust_tier` 등)과 활성 사실 정의(`expired_at IS NULL`; 읽기는 R-31이 `valid_until`까지 본다).
  - [ai-gateway](./ai-gateway.md): 사실 임베딩 `embedOne`(R-27 계열), 키 없음 판정 `isAvailable`(R-05·R-26), 질의 임베딩.
  - 호출자가 제공: `OperationContext`(`remote`, `sourceId`, `auth`, `sessionId`, `surfaceCeiling`), 엔진, 시계.
- 소유 상태·부작용: `facts` 행(INSERT/만료), 엔티티 페이지의 `## Facts` 펜스(쓰기 저널을 거쳐 DB 본문과 파일), `fact_withdrawals` 철회 장부, 쓰기 저널 행·영수증, `session_context_state`(delta 세션 커서, 7일·클라이언트당 상한으로 정리), 반환 페이지의 `last_retrieved_at`(fire-and-forget), 로컬 사용 로그(`protocol stats`). 읽기 verb는 위 외 상태를 바꾸지 않는다.

### 1.3 인터페이스와 데이터 의미

이름·파라미터·열거값은 외부 계약이므로 원문 그대로다. 표의 `*`는 필수. MCP 도구 이름은 verb 이름이고 CLI는 `gbrain remember <fact>`, `gbrain entity <name>`, `gbrain synthesize <question>`, `gbrain context-pack`, `gbrain delta`, `gbrain recall`(CLI 전용 경로가 먼저 처리, R-30), `gbrain forget <id>`(CLI 전용 명령). 입력 필드 전체와 스키마 원본은 C-01~C-05.

| 연산 | 입력 → 출력 | 의미·제약 |
|---|---|---|
| `remember` (scope write, 멱등 표시) | `fact`\|`items[1..20]`, `provenance`(≤500자), `ttl`, `valid_from`, `entity`, `infer_entity`(기본 true), `kind`, `visibility`, `replaces`, `content_origin`, 저널 공통 `request_id`·`source_id`·`expected_revision`·`force` → `{id:string, status, status_text, entity_slug, valid_until, degraded_dedup?, entity_inferred?, warnings?, hint?, superseded_fact_id?, replaced_by_caller?, write_request}` | `kind` 입력은 5개(`event\|preference\|commitment\|belief\|fact`, 기본 `fact`)로 동결, 응답에서는 `idea`도 올 수 있다. `visibility` 기본은 `world`이되 R-20. 단건 `provenance` 필수(R-10). `id`는 항상 문자열(불투명 사실 id). `replaces`·`content_origin`은 starter surface에서만 광고되지 않을 뿐 모든 surface에서 받는다(R-04) |
| `recall` (read) | `entity`, `question`, `query`, `budget_tokens`, `budget_policy`(`facts_first\|query_first`), `source_id`, `since`, `session_id`, `include_expired`, `supersessions`, `limit`(기본 50, 상한 100), `grep`, `include_pending`, `return_unit`, `return_window`, `min_trust` → `{facts[], total, facts_order, facts_degraded?, facts_calibration?, ambiguous_entity?, pending_consolidation_count?, protocol_version, results[]?, search_degraded?, budget_tokens?, budget_used?, dropped_count?, budget_packing?}` | 사실 팔과 페이지 팔(`query`)은 독립. 사실 행 필드는 R-35 |
| `entity` (read, 카드는 LLM 0회) | `name` 또는 `names[1..50]`, `source_id`, `prefer_source_id`, `variants`(기본 true) → `{protocol_version, found, latency_ms, card?, suggestions?, coverage?, text_mentions?, ambiguous?}` / `names`면 `{protocol_version, latency_ms, results[], found, missing}` | 미스는 오류가 아니라 `found:false`+근접 후보(`create_safety`). R-36 |
| `synthesize` (read, 비용 큼) | `question`*, `since`, `until` → `{answer, sources[], citations[], gaps[], cost{model,input_tokens,output_tokens,usd_estimate}, synthesis_status, pages_gathered, takes_gathered, evidence_truncated, warnings[], protocol_version}` | 도구 설명이 `[EXPENSIVE / SLOW`로 시작해야 적합(R-08). R-37 |

데이터 의미(이 기능이 정하는 값):

- **사실 id**: DB `facts.id`(정수)를 문자열로 `fact_id`/`id`에 넣는다. `recall` 응답은 옛 호환 필드 `id`(정수)도 함께 준다. `forget`·`replaces`는 이 문자열을 받는다.
- **펜스 행**(R-15): `| # | claim | kind | confidence | visibility | notability | valid_from | valid_until | source | context |` 10열(typed claim이 있으면 14열, 화자 표기가 있으면 15열).
- **상태 값**: `status ∈ {inserted, duplicate, superseded}`, 오류 `error ∈ {invalid_params, provenance_required, not_found, scope_denied, unavailable, budget_unsatisfiable(예약, 반환 안 함), internal}`.
- **토큰 단위**: `estimateTokens` = `ceil(비CJK 글자수/4) + CJK 글자수`. 바이트가 아니다(R-34, R-41).
- **시간**: 응답 시각은 ISO 8601, `delta` 커서의 시각은 마이크로초 6자리 `…ss.ffffffZ`.

| R-24 | 응답 모양과 대기 | 성공: `status_text`는 "remembered as fact #N" / "already knew this — kept fact #N" / "updated — fact #N supersedes the previous version" / (엔티티 없는 사본 연결) "linked — fact #N replaces #M, the same claim saved without an entity; nothing to forget". 분기는 `status`로 하라(`status_text`는 표시용). 엔티티가 없으면 `warnings:['NO_ENTITY'\|'ENTITY_LINK_FAILED']`와 `hint`(엔티티를 넣어 같은 주장을 다시 `remember`하면 사본이 대체되니 `forget`하지 말라 — 엔티티 없이 철회하면 모든 엔티티에서 철회되어 다시 저장 못 한다). `valid_until`은 ISO 또는 null. 영수증은 `write_request`에 붙는다. 호출자는 접수 직후 대기 시간(전송 계층이 받는 `wait_ms` 0~30000ms, 없으면 에이전트 기본 5000ms·CLI 30000ms, page-storage C-07; `wait_ms`는 `remember`의 선언된 파라미터 목록에 없고 전송 계층은 열지 않았다) 안에 `committed`를 기다리고 못 받으면 R-03의 `write_pending`. 대기 중·거절 오류의 영수증에는 `target{slug, entity_slug}`가 붙어 엉뚱한 페이지로 갔는지 알 수 있다 (C-14, C-13) | 실행 확인 (`outcome` 6모양) + 코드 확인 (대기) |

### 2.2 코드 읽는 순서

1. 계약의 모양: `verbs.ts`(앞 60줄 → `remember` → `RESPONSE_SCHEMAS`), 다음 `ops/facts.ts`의 `recall`·`context_pack`·`delta` 정의부(각각 `description`과 `params`가 에이전트가 읽는 지시문).
2. 저장: `memory-mutations.ts`의 `submitRememberMutation` → `planRememberTarget` → `memory-prepare.ts`의 `prepareMemoryMutation` → `single-prepare.ts`(`decideSingleFact`) → `facts-fence.ts`(`upsertFactRow`).
3. 읽기 묶음: `ops/facts.ts` `context_pack` 핸들러 → `context/turn-context.ts`(`assemblePack`, 렌더 함수) → `facts/meta-hook.ts`(핫 사실) → `verbs/entity-card.ts`.
4. 노출·트리거: `mcp/surface.ts` → `mcp/instructions.ts` → `commands/protocol.ts` → `verbs/conformance*.ts`.
- 구현 전략: 쓰기 verb는 "접수 전에 의미 검사를 하고 소비자 단계에서 다시 계산해 달라졌으면 충돌로 끝내는" 이중 검사 구조이고, 읽기 verb는 팔(arm)마다 실패를 격리해 응답을 부분적으로 줄 뿐 던지지 않는다. 읽기 포장기는 항상 같은 `estimateTokens`·`packToBudget`을 써서 `text`와 구조화 배열이 같은 최종 집합이 되게 한다.
