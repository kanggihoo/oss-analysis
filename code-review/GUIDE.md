## 0. 목적과 범위

### 목적
GitHub PR / GitLab MR 이벤트를 받아 **코드 변경, 관련 기존 코드, Jira 요구사항, 팀 규칙, 과거 리뷰 피드백**을 함께 검토하는 AI 코드 리뷰 서비스를 만들기 위해, 세 오픈소스가 각각 다음을 **실제 코드 근거와 함께** 어떻게 구현했는지 정리한다.

- 변경하지 않은 호출부·구현체·설정·테스트까지 **동적으로 탐색**하는가
- 한 번의 LLM 호출로 끝나는가, 도구를 호출하며 **반복(Agent Loop)** 하는가
- 리뷰 결과(finding)를 **검증**하는가
- 과거 피드백을 **다음 PR에서 활용**하는가
- 팀 규칙과 Jira 요구사항을 코드 근거와 **대조**하는가

배경: 작성자는 PR-Agent를 써 본 경험이 있고, 고정된 diff 주변 줄 확장만으로는 문맥이 부족하다고 느꼈다. 단, **PR-Agent가 단발성이라고 미리 단정하지 않고** 코드로 확인한다. 고정 규칙 전처리 자체는 배제하지 않는다. 핵심은 전처리 이후에도 필요한 문맥을 동적으로 확보할 수 있는지다.

| 레포 | 언어 | 우리 서비스 관점에서 볼 것 | 최종 질문 |

## 2. 코드 기준 고정 (SHA)

### 2.1 분석 대상과 고정 SHA

`repos.lock.tsv`의 현재 값이다(2026-10-13 clone 시점 기본 브랜치 HEAD).

| 이름 | URL | 브랜치 | SHA | 커밋일 | 라이선스 |
|---|---|---|---|---|---|
| pr-agent | https://github.com/The-PR-Agent/pr-agent | main | `330f0813b5fe0d1f54b794077c2d02aa85a1fb63` | 2026-10-11 | MIT |
| open-code-review | https://github.com/alibaba/open-code-review | main | `57273a9ea28548b94b3d67c247ff13a63c01fc47` | 2026-06-21 | Apache-2.0 |
| kodus-ai | https://github.com/kodustech/kodus-ai | main | `45676c5fe7ac016b6206ccea006e459677d92842` | 2026-10-12 | `license.md` + `license_ee.md` (Community / Enterprise 분리. 경계는 분석 시 확인) |

- 이 값들은 **LICENSE 파일 첫머리 기준의 1차 확인**이다. 하위 디렉터리별 라이선스는 분석 중 다시 확인한다.
- `repos/`는 전체 clone 상태이며 **고정 SHA의 HEAD가 아닐 수 있다**. 분석 시작 전에 2.2절로 SHA를 맞춘다. `main`은 계속 바뀌므로 의존성 목록도 **체크아웃한 커밋에서 다시 확인**한다.

### 2.2 고정 절차

```bash
cd ~/Desktop/oss-analysis/code-review
git -C repos/<name> fetch origin <sha>
git -C repos/<name> checkout <sha>          # detached HEAD
git -C repos/<name> rev-parse HEAD          # <sha>와 같은지 확인
git -C repos/<name> status --porcelain      # 비어 있어야 함 (clean)
```

지켜야 할 규칙:
- 분석하는 동안 `repos/<name>`에서 `pull`, 브랜치 이동, 파일 수정을 하지 않는다. **라인 번호는 고정 SHA에서만 유효하다.**
- SHA를 갱신하면 기존 보고서의 라인 번호가 틀어진다. `reports/<repo>/`를 새로 쓰거나 문서 머리의 SHA를 바꾸고 근거를 다시 검증한다.
- 클론한 코드는 **읽기만** 한다. 설치, 빌드, 실행을 하지 않는다. 테스트나 작은 저장소 실행 사례가 꼭 필요하면 사용자와 먼저 합의한다. 실행하지 않은 항목은 "정적 추적 결과"라고 표시한다.
- 원본 레포에는 `graphify-out/`(open-code-review) 같은 분석 산출물이 섞여 있을 수 있다. 이런 파일은 분석 근거로 쓰지 않는다(분석 후보일 뿐).

## 3. 근거 표기 규칙

### 3.1 위치 표기

모든 주장에는 **`레포 루트 기준 상대경로:시작줄-끝줄`** 형식으로 근거를 붙인다.

```text
internal/llmloop/loop.go:42-118
```

- 함수/클래스/메서드가 있으면 식별자도 함께 적는다.
- 핵심 근거 1~2개에는 **SHA 고정 permalink**를 붙인다. `main` 링크는 쓰지 않는다.
  ```text
  https://github.com/<owner>/<repo>/blob/<sha>/<path>#L42-L118
  ```
- 라인 번호는 파일을 직접 열어 확인한 값만 적는다. grep 결과를 그대로 옮기지 않는다.
- 근거 표 형식:

  | 구분 | 위치 | 식별자 | 설명 | 검증 |
  |---|---|---|---|---|
  | 진입점 | `cmd/review.go:20-60` | `runReview()` | 리뷰 시작 | 코드 확인 |

### 3.2 프롬프트 인용

리뷰 기준·종료 조건·검증 지시는 프롬프트에 있는 경우가 많다.
- 핵심 문장은 원문 그대로 짧게 인용하고 바로 아래에 한국어 번역을 붙인다.
- 길면 전문을 옮기지 않고 위치와 요약만 적는다.
- 프롬프트가 설정·DB·템플릿 파일에 있으면 그 파일과 키 경로를 적는다.

### 3.3 검증 수준과 기능 지원 수준 (두 축을 분리)

**검증 수준** (근거를 얼마나 확인했는가, 상위 규칙과 동일):
- **`코드 확인`**: 코드를 직접 열어 확인
- **`실행 확인`**: 실제로 실행해서 확인
- **`추론`**: 코드 정황으로 짐작. 반드시 근거를 함께 적는다
- **`미확인`**: 확인하지 못함

**기능 지원 수준** (기능이 구현돼 있는가, 비교 표용):
- **지원**: 호출 경로와 데이터 흐름을 코드로 끝까지 추적함
- **부분 지원**: 일부 경로만 있거나 조건부 / 선택 설치 / 일부 Provider만
- **미지원**: **충분히 추적한 범위에서** 없음을 확인함. 검색 실패만으로 단정하지 않는다. 어디를 찾아봤는지 적는다
- **미확인**: 확인하지 못함

규칙:
- README나 docs, 제품 문구만 본 것은 `코드 확인`이 아니다. **제품 문구와 실제 구현을 구분**하고, 다르면 코드 기준으로 쓰며 차이를 기록한다.
- **패키지 선언은 기능의 증거가 아니다.** 의존성에 있다는 사실만으로 Agent Loop, MCP 사용, Jira 연동, 벡터 메모리, 샌드박스 사용을 단정하지 않는다. import → 호출 위치 → 리뷰 단계까지 이어서 확인한다.
- **기록만 있고 조회가 없으면 학습이 아니다.** 메모리를 쓰는 코드만 있고 다음 리뷰에서 읽는 코드가 없으면 "피드백 학습"이라고 부르지 않는다.

## 4. 공통 분석 항목

모든 레포에서 아래 항목을 같은 번호로 조사한다. 해당 사항이 없으면 "없음"과 **어디를 찾아봤는지**를 적는다. 각 항목 끝에 기능 지원 수준(3.3절)을 한 줄로 적는다.

### Q1. 실행 경로: 이벤트에서 댓글 게시까지

진입점에서 최종 게시까지 **실제 함수 호출 순서**를 따라간다.

- 진입점: CLI / GitHub Action / 웹훅 서버 / 워커. 현재 커밋의 디렉터리 구조부터 확인한다
- 단계: 입력 수집 → (웹훅 검증 → 이벤트 정규화 → 작업 발행 → 소비) → 코드 확보 → 리뷰 → 검증 → 후처리 → 게시
- 명령/기능별 경로 분리 (예: PR-Agent의 `/review`와 `/improve`)
- **mermaid 호출 흐름도 1개**. 노드마다 코드 위치를 붙인다

### Q2. 코드 접근과 Diff 처리

**코드 접근**
- 입력 경로 구분: 로컬 작업 트리 / clone / Git Provider API / 샌드박스
- Base / Head / Merge Base, 미커밋 변경 처리
- 파일 원문(변경 전/후) 확보 방법
- 실행 중 SHA 일관성: 리뷰 도중 Head가 바뀌면 어떻게 되는가
- "전체 저장소에 접근 가능하다"와 "전체 코드를 모델에 넣는다"를 구분

**Diff 처리**
- Provider가 만드는 파일 변경 객체의 필드와 생성 경로
- rename / delete / 바이너리 / 대규모 변경 처리
- 주변 줄 확장의 **실제 조건과 알고리즘**. 함수 경계 / 언어 구조를 쓴다면 AST인지 정규식·휴리스틱인지
- 토큰 초과 시: 파일 순서, 제외, 압축, 분할, 다중 호출 조건
- Provider API가 diff를 잘라 반환했을 때 복구하는가
- old/new 라인 번호 → 모델 입력 번호 → 게시할 인라인 위치 변환 (GitLab은 SHA·경로·old/new 라인 매핑)
- 문자열 diff와 diff 파싱 라이브러리가 각각 맡는 로직 분리
- **짧은 예 1개**: 입력 diff → 내부 객체 → 확장/압축 결과 → 모델 입력

### Q3. 문맥 확보와 동적 탐색

| 구분 | 확인할 것 |
|---|---|
| 고정 문맥 확장 | 규칙(주변 N줄, 함수 단위 등)으로 **프로그램이 자동 수집**하는 것 |
| 동적 탐색 | **모델이 요청해서** 읽는 것: 변경하지 않은 호출부, 인터페이스 구현체, 설정, 테스트 |
| 탐색 수단 | grep / glob / 파일 읽기 / AST·LSP / 임베딩 / 명령 실행 / MCP. 도구가 심볼 관계를 직접 이해하는가, 모델이 추론하는가 |

- 도구별 **입력·출력 스키마**를 기록한다
- 자동 수집되는 파일과 모델이 요청해서 읽는 파일을 반드시 분리한다
- "변경하지 않은 호출부를 찾는" **짧은 실행 예**를 낸다. 실행하지 못하면 정적 추적임을 표시한다
- 파일 그룹별 리뷰에서 **파일 간 결함을 놓칠 가능성**

### Q4. Agent Loop

반복의 **단위**부터 구분한다. 아래는 서로 다른 것이다.

| 구분 | 설명 |
|---|---|
| Agent Loop | 모델이 도구를 호출하고, 결과를 대화에 넣어 다시 추론 |
| 재시도 / fallback | 실패 시 같은 입력을 다시 보내거나 다른 모델로 교체 |
| 다중 호출 | 파일별·청크별로 같은 프롬프트를 여러 번 |
| 다단계 파이프라인 | 단계마다 다른 프롬프트를 고정 순서로 (생성 → 검증 등) |

확인할 것:
- 최초 모델 입력 재구성: diff, 원본 파일, 규칙, 배경 설명 중 무엇이 들어가는가
- **모델이 선택하는 것 / 프로그램이 고정하는 것** 표시
- 상태 구조, 도구 결과의 대화 기록 반영, 병렬 도구 호출
- **종료 조건 각각**: 정상 종료, 도구 호출 없음, 최대 반복, 토큰·시간 한도, 취소, 모델 오류, "충분히 조사했다"는 판단
- 오류 이후 재시도 범위
- LiteLLM, Vercel AI SDK 같은 추상화 라이브러리를 쓴다는 사실만으로 에이전트 구조라고 해석하지 말고 **실제 completion / Tool Calling 경로**를 추적한다

**상태·입력·종료 조건 표**를 작성한다.

| 단계 | 반복 단위 | 입력(상태) | 모델 선택 | 프로그램 고정 | 종료 조건 | 위치 |
|---|---|---|---|---|---|---|

### Q5. 검증 (finding 필터링)

- 구조화 출력(스키마 검증)과 **별도 결함 검증 단계**를 구분
- 제안 라인 유효성 검증이 **의미적 결함 검증**까지 하는가 (보통 아니다)
- finding 생성과 검증이 같은 모델·같은 문맥인가, **독립 실행**인가
- 검증자가 **추가 파일을 읽을 수 있는가**, 기존 설명만 다시 평가하는가
- 오탐 필터링, 결과 중복 제거(파일 그룹 간, 재실행 간)
- 평가 스크립트(evals)가 있으면 실제 리뷰 경로와 연결되는지, 오탐·누락을 어떻게 측정하는지

### Q6. 증분 리뷰

- 새 커밋 이후 비교 기준 (마지막 리뷰한 SHA? PR 전체?)
- 이벤트 중복, 동일 PR의 연속 업데이트, 작업 재시도에서 **리뷰가 중복되지 않는 장치**
- 실행 도중 Head SHA 변경 시 오래된 결과를 **취소·폐기**하는가
- 이전 코멘트의 유지 / 수정 / 해결(resolve) 처리

### Q7. 장기 메모리 (쓰기와 읽기 양쪽을 추적)

실행 대화 / 실행 체크포인트 / 같은 PR 이력 / **PR 간 영속 메모리**를 구분한다.

- **쓰기**: 댓글 답변·반박·수정·승인 중 어떤 이벤트가 저장되는가. 원문 로그를 재사용 가능한 지식으로 변환하는 로직이 있는가
- **저장**: 저장소 종류, 스키마, 출처(PR·댓글·SHA), 적용 범위
- **읽기**: 다음 PR에서 조회하는 함수와 검색 조건 (키워드 / 벡터 / 경로 / 시간 / 심볼)
- **수명 관리**: 신뢰도·승인 상태·삭제·충돌·과거 결정 무효화
- 무응답 / resolve / 코드 수정을 **동의로 해석**한다면 그 위험과 보정 구현
- 읽기 방식 비교: 최초 입력에만 주입 vs 호출 가능한 도구로 제공
- 쓰기만 있고 조회가 확인되지 않으면 "피드백 학습"이라 하지 않는다
- 유사 이슈 검색(similar-issue) 같은 기능을 팀 메모리와 혼동하지 않는다. 데이터 원천·인덱싱·검색 경로를 각각 분석한다

### Q8. 팀 규칙

- 범위 계층: 전역 / 조직 / 팀 / 저장소 / 경로별 / 명령별. 스키마와 소유자
- 우선순위와 충돌 처리 (자연어 규칙, 기본 설정, 파일 규칙, 사용자 입력)
- 생성·편집·승인·버전 관리·비활성화 경로
- 개발자 피드백에서 규칙을 **추출**하는 과정이 있는가 (트리거, 검증 단계)
- 리뷰 시 규칙을 **읽는 쿼리**와 **모델 입력 위치**(어느 메시지, 어느 순서)
- 구분: 커스텀 프롬프트 / 저장·승인·버전 관리되는 팀 규칙 / 자동화된 정책 엔진
- 규칙 파일·배경 파일을 어디서 로드하고 어떤 메시지에 넣는가

### Q9. Jira / 요구사항

- 이슈 식별 (브랜치명, PR 제목, 링크), 인증, 필드 추출 (Acceptance Criteria), 입력 삽입 위치
- 구분: **요구사항 텍스트를 입력에 넣는 것** vs **조건별로 구현 근거를 찾아 판정하는 것**
- 연결된 이슈 전체 요구사항과 **이번 PR 범위**를 구분하는 구현이 있는가
- 미지원이면 요구사항 수집 / 조건별 근거 탐색을 넣을 **구체적 확장 지점**(함수·인터페이스·리뷰 단계)을 제시 (Q12 의견과 연결)

### Q10. SaaS: 인증, 큐, 격리, 장애 복구

- 인증: GitHub App 설치 토큰, GitLab 토큰의 수명·권한·보관 방식. 웹훅 서명 검증, 이벤트 필터링
- 큐: 발행·소비·ack/nack·재시도 정책, 실패 작업 저장, 장애 복구
- **테넌트 격리**: DB 쿼리, 큐 메시지, 캐시 키, clone 경로, 샌드박스, 검색 요청, 벡터 검색 필터, 메모리 조회마다 **조직 범위가 전달되는지**. 팀 A의 코드·규칙·메모리가 팀 B 리뷰에 섞이지 않는 근거
- 외부 서비스 장애·지연·비용이 어느 리뷰 단계에 영향을 주는가
- 단일 사용자 CLI 도구라면 "해당 없음"과 서비스 워커로 옮길 때 **분리할 의존성**(TUI, 파일 시스템, 환경변수)을 적는다

### Q11. 의존성

**조사 시작점은 매니페스트의 선언이다.** 선언 → 실제 사용 → 설치 버전을 모두 확인한다.

- 선언(버전 범위)과 **lockfile 해석 버전**을 구분한다
- 분류: 직접/간접, 필수/선택, 런타임/개발, base / extras / dependency group, 로컬 라이브러리 / 외부 서비스
- 각 주요 패키지를 **import → 호출 함수 → 리뷰 단계**까지 연결한다
- 자체 구현(루프·검색·검증)과 SDK가 제공하는 기능의 **경계**
- 외부 서비스·바이너리 요구(모델 API, MCP 서버, git, Docker, 샌드박스, DB, 큐)는 **별도 표**로 정리
- 제거·교체 시 영향, 라이선스, API 비용은 근거가 있는 범위에서만
- 최소 실행 구성: 문서·설정(Compose, 환경변수, 모듈 초기화) 근거로 제시. 숫자는 측정하지 않았다면 만들지 않는다

**의존성 표**

| 패키지 | 선언 버전 | 해석 버전 | 분류 | 호출 위치 | 역할 | 교체·제거 영향 | 근거 |
|---|---|---|---|---|---|---|---|

### Q13. 자격증명 관리: 비공개 저장소 접근 토큰

비공개 저장소의 diff·파일·clone·댓글 게시에는 토큰이 필요하다. **토큰이 어떻게 만들어지고, 어디에 저장되고, 어떻게 쓰이는지**를 코드로 추적한다. 실제 값은 절대 기록하지 않는다(변수명·키 경로만).

- **자격증명 종류**: PAT / GitHub App 설치 토큰 / OAuth / GitLab 프로젝트·그룹 토큰 / `CI_JOB_TOKEN` / 웹훅 시크릿 / LLM API 키 / Jira·MCP 토큰. 플랫폼별로 지원하는 종류와 필요한 **권한 범위(scope)**
- **주입 경로**: 환경변수 / 설정 파일 / DB / 시크릿 매니저 / 요청 헤더·페이로드. 어느 코드가 읽는가
- **저장**: 평문 / 암호화(알고리즘과 키 위치) / 저장 안 함. 테넌트(조직·팀)별로 구분되어 저장되는가
- **수명과 갱신**: 설치 토큰 발급·만료·재발급, OAuth refresh, 만료 시 실패 처리
- **사용 지점**: Provider API 호출, **git clone/fetch**(토큰이 URL·헤더·credential helper 중 어디에 들어가는가), 샌드박스·워커로의 전달, 댓글 게시
- **유출 방지**: 로그·에러 메시지·세션 기록·clone된 `.git/config`에 토큰이 남는가, 마스킹, clone 후 정리
- **CLI/GitHub Action/웹훅 서버/SaaS**별로 달라지는 점
- 서비스 설계용 **의견**: 우리 서비스(여러 팀, 비공개 저장소)에 맞는 방식과 직접 만들어야 할 부분(Q12와 연결)

### Q12. 우리 서비스에 적용 (분석자 의견)

- **가져올 것 / 직접 만들 것 / 운영해야 할 의존성**
- 재사용 / 재구현 판단과 이유
- 라이선스상 코드 재사용이 가능한가, 아이디어만 참고해야 하는가
- 새로 설계해야 할 경계 (동적 탐색, PR 간 메모리, Jira 근거 검증 등)

이 항목은 코드 근거가 아니라 **분석자 의견**이므로 문서 안에 "의견"이라고 명시한다.

## 5. 레포별 중점 항목

공통 항목(Q1~Q13)을 모두 하되, 레포마다 아래는 특히 깊게 판다. 아래 경로는 **탐색 후보**이며, 현재 SHA에서 존재와 역할을 확인한 뒤 쓴다.

### pr-agent — Diff 전처리, Provider, 게시 모듈

| 중점 | 확인할 것 |
|---|---|
| Diff 전처리 (최우선) | • Provider 파일 변경 객체(필드, 생성 경로)<br>• 주변 줄 확장 조건·알고리즘, 함수 경계가 AST인지 휴리스틱인지<br>• 토큰 초과 처리(순서·제외·압축·분할), API가 diff를 자른 경우 복구<br>• old/new 라인 번호 변환, 게시 위치 변환<br>• 문자열 diff vs `unidiff` 책임 분리<br>• 입력 diff → 내부 객체 → 확장/압축 → 모델 입력 짧은 예 |
| 명령별 경로 | `/review`, `/improve` 등의 호출 경로 분리: 프롬프트 구성 → LLM 핸들러 선택 → 응답 파싱 → 후처리 → 게시 |
| 구분표 | 고정 문맥 확장 / 동적 탐색 / 재시도·fallback / Agent Loop. Tool Calling이 있다면 도구와 종료 조건. **LiteLLM 사용 ≠ 에이전트 구조** |
| Provider | GitHub/GitLab 공통 인터페이스와 차이, GitLab 라인 매핑, 토큰·App 인증·웹훅 검증·이벤트 필터링·중복 실행 |
| 증분 리뷰 | 새 커밋 이후 기준, 기존 댓글 처리 |
| Jira | 이슈 식별·인증·필드 추출·삽입이 **실제로 어디에 있는지**. `atlassian-python-api` 선언만으로 Jira 연동을 주장하지 않는다 |
| 메모리 | 같은 PR/다른 PR 구분. `similar-issue`는 팀 메모리가 **아님**. 피드백 → 다음 PR 쓰기/읽기 경로가 없으면 없는 범위와 근거를 명시 |
| 의존성 | Provider SDK는 optional-dependencies, 벡터 DB는 similar-issue dependency group이다. **기본 설치에 모두 포함된다고 해석하지 않는다**. `GitPython`이 모든 Provider의 clone을 뜻하는지 검증. LangChain extras가 기본 핸들러와 어떻게 다른지. CLI / GitLab 웹훅 / GitHub App별 **최소 설치 구성**. Dockerfile·설치 스크립트·`uv.lock` 확인 |
| 우선 사례 | 함수 수정, 호출부의 숨은 전제, rename, 큰 diff, GitLab 라인 매핑 |
| 탐색 후보 | `pr_agent/algo`, `pr_agent/git_providers`, `pr_agent/tools`, `pr_agent/servers`, `pr_agent/settings`, `pyproject.toml`, `uv.lock`, `docker/` |

### open-code-review — 리뷰 실행, 반복 탐색, 검증

| 중점 | 확인할 것 |
|---|---|
| 리뷰 실행과 종료 (최우선) | • CLI 진입점 → 입력 수집 → 파일 그룹화 → 리뷰 → 검증 → 출력 호출 관계<br>• 반복의 단위(Tool Calling / 같은 입력 재리뷰 / 별도 검증)<br>• 모델 선택 vs 프로그램 고정<br>• 상태 구조, 도구 결과 반영, 병렬 도구 호출, 오류 재시도<br>• 종료 조건 각각(정상, 도구 없음, 최대 반복, 토큰·시간, 취소, 모델 오류) |

| 코드 확보 | 로컬 작업 트리 / clone / Provider API 중 실제 입력 경로, Base/Head/Merge Base, 미커밋 변경, diff 파싱·삭제·rename·대규모 변경, 라인 매핑 |
| 도구 | 파일 읽기·검색·명령 실행·MCP 도구의 입출력 스키마. grep vs AST/LSP vs 모델 추론 구분. 호출부·구현체를 찾는 짧은 실행 예 |
| 메모리·규칙·Jira | 영속 메모리가 보이지 않으면 **검토한 저장 코드와 범위**를 제시하고 미확인/미지원 판단을 설명. 규칙·배경 파일 로드와 메시지 위치. Jira가 없으면 요구사항 수집·요구사항별 근거 탐색의 삽입 함수/인터페이스 제안 |
| 서비스화 | CLI 엔진을 서비스 워커에서 실행하려면 분리할 TUI·파일 시스템·환경변수 의존성 |

### kodus-ai — 서비스 전체 경로, 규칙, 메모리, 격리

| 중점 | 확인할 것 |

## 8. 진행 순서와 완료 기준

### 진행 순서
1. **레포 하나 시작**: 2.2절로 SHA를 고정하고 `repos.lock.tsv`와 `00-overview.md` 메타데이터를 채운다. 기존 `reports/`·`wiki/`에 해당 레포 문서가 있는지 먼저 확인한다(중복 방지). 예: 상위 `reports/open-code-review`가 있으면 참고하되 코드는 다시 검증한다.
2. **진입점부터 추적**: 현재 디렉터리 구조를 확인하고, 이벤트 또는 CLI 입력에서 게시까지 따라간다(Q1).
3. **문맥과 루프**: 모델 입력을 재구성하고(Q4) 문맥 확보 방식을 구분한다(Q3), 검증을 본다(Q5).
4. **Q2, Q6~Q10**을 채운다.
5. **의존성(Q11)**: 선언 → import → 호출 위치 → 리뷰 단계 순으로 연결한다.
6. **Q12**와 `next.md`를 정리한다.
7. 3개가 끝나면 **`comparisons/`**를 작성한다.

권장 레포 순서: **pr-agent → open-code-review → kodus-ai**.
이미 써 본 pr-agent로 "고정 문맥 확장"의 기준선을 코드로 확정하고, 그다음 open-code-review에서 반복 탐색·검증을 보고, 구조가 가장 큰 kodus-ai를 마지막에 본다.

### 레포 하나의 완료 기준
- [ ] 모든 문서 머리의 SHA가 `repos.lock.tsv`와 같다.
